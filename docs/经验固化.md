## E1 · 判定"源不可用"前，必须把它的全部工具试完

**现象**（L1，2026-11-03，DeepEP）：

| 步骤 | 动作 | 返回 |
|---|---|---|
| 1 | `GET deepwiki.com/deepseek-ai/DeepEP` | HTTP 429 + `Vercel Security Checkpoint` |
| 2 | MCP `tools/list` | 三个工具：`ask_wiki_question` / `read_wiki_contents` / `read_wiki_structure` |
| 3 | 只调 `read_wiki_structure` | 页面标题列表，**无文件路径** → 误判"MCP 不能用于命中判定" |
| 4 | 改走 HTML 抓取 | 不稳定，时好时 429 |
| 5 | 补调 `read_wiki_contents` | **196KB 正文，含 10 个仓库内真实路径** → 这才是正路 |

**根因**：把"入口 A 不含证据"当成"源不含证据"；把"一次 429"当成"源不可用"。二者都是用一个样本否定一个集合。

**修法**：
- 结论必须附「试过哪些入口 + 各自返回」，形如 `tried: [html→429, mcp/structure→仅标题, mcp/contents→196KB 含10路径]`。
- 报告里的 `blocked` / `unavailable` 必须带 HTTP 状态或错误类型，禁止只写"不可用"。
- 新增数据源时，探测代码必须能把"试过什么"写进报告原因字段。

**适用边界**：
- **确定性失败**（401/402/404、MCP 明确 `isError`）一次即足，不需要穷举；
- 本规则只针对"疑似不可用"（429 / 超时 / 空页 / 模板页）这类可能只是单个入口的问题；
- 入口 > 5 个或单次 > 60s 时，允许"试完前 N 个 + 明确记录未试项"，但结论必须降级为「**部分验证**」，**不得写成不可用**。

## E2 · 上下文一次吃满上限，等于用最贵的方式做最浅的分析

**现象**：首版把 20 个源码切片全塞进 fast 档 prompt，估算 **114,229 tok**，逼近 `per_run_prompt_tokens = 120,000` 的上限；单次成本约为最终版的 6 倍。

**根因**：把 `per_run` 上限当成了"目标值"。上限是**保险丝**，不是配额；fast 档只做"取舍识别"，不需要整仓。

**修法**：切片前先裁剪——**6 个文件 / 每文件 6000 字符**，估算降到 **17,354 tok**；文件按依赖图入度降序选（被引用多的优先）。实测真实 `usage.prompt_tokens = 21,803`（估算偏低 25.6%，因为 system prompt 与文件清单未计入）。

**适用边界**：这是 fast 档的取值。strong 档要读更多上下文时，应通过配置放大并**重新实测定价**，不能沿用 6/6000；文件字符截断对"需要跨文件追踪调用链"的任务不适用（会截断证据）。

## E3 · 累计成本双计：排除"本次事件"时用错了身份

**现象**：报告「累计」显示本周 ¥0.0972 / 45,066 tok，正好是单次（¥0.0459 / 22,304 tok）的两倍。

**根因**：写台账时 `run_id = sha256(repo|as_of|requested|actual|reason)`，而计算累计时用 `run_id = ...|purpose` 去排除本次事件——两套身份不一致，本次事件没被排除，于是"历史（含本次）+ 本次"被加了两次。

**修法**：不靠 `run_id` 排除，改为按 **`(repo, as_of, purpose)`** 过滤掉本次分析的调用事件。语义更稳：同一 `as-of` 就是同一次分析。

**适用边界**：若将来同一 `as-of` 允许对同一仓库跑**多个 purpose**（如 fast 摘要 + strong 深挖），过滤必须带上 purpose（已带），否则会把另一个 purpose 的真实花费也排除掉。

## E4 · 报告数字随"本次是否命中缓存"变化 → 幂等当场失效

**现象**：首次运行成本行是「本次 ¥0.0476（1 次调用，api）」，重跑（结果缓存命中）变成「0 次调用，cache）」——同一 `--as-of` 两次报告字节不同。

**根因**：把**进程行为**（这次有没有发请求）写进了**分析产物**。报告描述的是"这一次分析"，不是"这一次进程"。

**修法**：成本行只依赖该分析**已固化的结果**（`data/llm_cache` 里的 usage），与本次进程是否命中缓存无关：`本次 ¥0.0459（模型调用 1 次）`。进程级的真实花钱情况交给 `cost` 命令（读全量台账）。

**适用边界**：只适用于"结果会被持久化"的调用。若某类调用不缓存（如每次都要实时的探测），其成本天然不可幂等，应移出报告、只记台账。

## E5 · `quota_state` 随调用次数漂移，同样破坏幂等

**现象**：同一 `--as-of` 第二次运行时，报告里的 `fast 0/3` 变成 `fast 1/3`。

**根因**：`quota_state` 直接读台账里"本周已用次数"，而本次分析自己的调用在上一次运行中已落账 → 每次重跑分母不变、分子 +1。

**修法**：报告中的配额统计**排除本次分析自身的调用**（与 E3 同一过滤器）。改后稳定为 `fast 0/3`，含义变成"**本次分析之外**本周已用多少"——这恰好也是读者关心的（它解释"为什么会降级"）。

**适用边界**：如果将来要做"配额看板"，必须用 `cost` 的全局口径，不能拿报告里的 `quota_state` 当真值；两者语义不同，已在报告成本行标注。

## E6 · lint 扫到了 vendored 源码

**现象**：`ruff check .` 在 `data/snapshots/deepseek-ai__DeepEP/2026-11-03/src/**` 报出 `I001` / `F401` / `E501` 几十条，四门禁直接红。

**根因**：`data/` 存的是**别人的源码切片**（证据原件），`ruff .` 默认递归全仓；把它当自己的代码检查既无意义，也会诱导人去"修"证据（篡改证据比 lint 红更严重）。

**修法**：`pyproject.toml` 加 `extend-exclude = ["data", "reports", "site"]`；`mypy` 本来就只 `files = ["osslens"]`，无需改。同时在 `data/` 的语义上明确：**只读证据，不参与任何门禁**。

**适用边界**：任何"把外部内容落到仓库内"的目录（抓取的源码、生成的报告、站点产物）都应排除；但**排除不等于不检查**——这些内容要靠"证据回查测试"（`test_real_featcard_evidence_points_to_real_lines`）保证正确性，而不是靠 linter。

## E7 · `raw.githubusercontent.com` 不可达 → 用 codeload 拿整仓

**现象**：按文件逐个取源码时，`raw.githubusercontent.com` 在本环境返回 **000（连接失败）**；逐文件走 Contents API 又要为每个文件消耗一次 GitHub API 额度（匿名仅 60 次/小时）。

**根因**：默认假设"GitHub 的各个域名都通"。实际可达性按域名不同；且逐文件取法把"文件数"变成了 API 成本。

**修法**：改用 `https://codeload.github.com/<owner>/<repo>/tar.gz/<sha>`——**1 次请求拿整仓**、**不占 GitHub REST 额度**（不同域名、不同配额），本地解包后按需切片落盘。同一 commit 内容不可变，切片可缓存复用。

**适用边界**：
- 仓库体积大时（> 数十 MB）要加大小上限，否则下载成为新瓶颈；
- tarball 是**快照**，不能用于"跟踪最新"；必须用 commit sha 固定；
- 若某仓库禁止 tarball 下载，回退逐文件 API，并在报告里标注降级来源。
