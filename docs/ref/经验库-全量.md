> **定位**：跨项目可迁移的**原则、判据与陷阱清单**，不是任何单个项目的总结。
> **来源**：AI Pulse（V1/V2）、AI Scholar（V1/V2）、my-LLM-from-scratch v2 重构、refactor-pilot 六个项目全过程的踩坑与复盘，去重整合而成。
> **格式**：每条 = **现象 → 判据**。判据是可以直接执行或检查的规则。

## 0. 怎么用这份文档

### 0.1 阅读方式

| 场景 | 读哪 |
|---|---|
| 新项目开工前 | §16 一页速查卡 |
| 遇到具体问题 | 按章节查（章节按主题而非按项目划分） |
| 阶段性收尾 | §15 收尾检查清单 |
| 写指令 / 推进长任务 | §13 阶段推进 SOP、§14 提示词模板 |

> ⚠️ **不要全量读长文档，给精确必读清单。**
> 新会话/新阶段恢复时，通读上千行的库会稀释注意力，且衰减后的会话读不完也记不住。
> 正确做法：给一份**启动包**（一句话定位 + 已完成 + 关键决定 + **必读章节清单**），
> 只点名与本轮任务相关的那几节，并标明哪些内容**已衰减、需回贴原文**。

### 0.2 三条元习惯（贯穿全文）

1. **用数据说话**：能用实测数字回答的，不用形容词。凡涉及成本、性能、覆盖率的判断，必须落到实测数字。
2. **先核实后判断**：查不到就说查不到，不编理由。
3. **质量优先于进度**：不确定就停下来问，不为推进而猜测。
4. **及时复盘与归档**：每次犯错、反思、得到教训，**当场归档，不攒到最后**。归档要写清"错在哪 + 正确表述是什么"，不只写"下次注意"。
5. **如无必要，勿增实体**：遇到"要不要加个特例分支"，先问**能不能通过放宽主参数消除这个特例**。判据：一个特例换来的收益 vs 它引入的状态空间——**后者常被低估**。

### 0.3 继续 merge 的规则（后续新增经验时遵守）

1. **先归章，再落笔**。新增经验优先并入已有条目（补充证据或强化判据），确实无处可归才开新条目。
2. **只收能指导行动的判据**。纯感想、纯过程叙述不进库；"下次注意"这类不写成判据就不收。
3. **区分通用与项目专用**。脱离具体项目后仍能指导行动 → 进主文；绑定特定数据结构/模型代号/成本量级 → 进 §17 附录。
4. **保留来源与反例**。每条尽量附一句真实现象，它是判据可信度的证据。
5. **改文档前先通读**（§11.10），插入章节前先核对编号（§11.9）。
6. **★ 每次 merge 后做覆盖度核对**：抽出原始文档的全部章节标题，逐条检索验证已覆盖；命中数为 0 的必须显式说明"为何不收"，**不能静默丢弃**。
   > 立这条的起因：v1.0 整合后自查发现漏了 14 条（诊断方法论、删除类操作五条、描述与产出一致、双仓库裂缝等）。根因是"读一遍再重写"依赖记忆，必然有洞——**先建核对清单再打勾**才靠得住。

## 1. 元原则

> 这六条是全文的底色，后面所有判据都是它们的具体化。

| # | 原则 | 一句话 |
|---|---|---|
| 1 | **状态一致性 > 代码质量** | 文档与代码对不上、描述与产出对不上、新旧文档互相冲突——这些都不报错，但会慢慢抽掉协作的可信基础 |
| 2 | **能发现比不出现更重要** | 缺陷不可能清零（尤其用了 LLM 的系统），追求"出问题能被发现"，可观测性优先级高于功能完备性 |
| 3 | **用户的判断是最强的检测器** | 有一类问题（该出现的重要信息没出现）所有自动化都测不出，只有真用且懂领域的人会发现 |
| 4 | **凡能实测，就不要推断** | 推断只能用于"要不要做"，不能用于"做成什么样" |
| 5 | **让正确性可被检查，而不是被保证** | 状态落盘 = 进度可检查；反向测试 = 规则可证伪；不做清单 = 范围可检查 |
| 6 | **踩过的坑要变成下次能自动挡住的规则** | 事故之后问的不是"怎么修好它"，而是"怎么让它下次不可能悄悄发生" |

## 2. 事实与核实（最容易出错的一族）

### 2.1 无知不是证据

**现象**：没读过某份文档，却断言"它没有这条规定"。

> **判据**：「我没看到」和「它不存在」是两件事。任何否定性断言（没有 / 不支持 / 不存在 / 未记录）必须先实际检索一次，并在结论里附上检索方式。

### 2.2 「已实现 / 已定 / 已完成」是待验证声称，不是事实

**现象**：文档写着"已决定 X"，代码里是空的；测试过了，迁移没生成；迁移有了，生产数据没覆盖。

> **判据**：看到"已定/已完成/已处理"字样，默认它是**待验证声称**。说"已实现"前分三层确认——**代码已合入 / 迁移与配置已生效 / 真实数据已覆盖**，缺任一层都不算完成。
> 反过来同样成立：**"我新增了 X"必须先核实再说**（本条被违反过 12 次，靠自觉挡不住，见 §12.3）。

### 2.3 文档没记 rationale ≠ 当初是拍脑袋定的

**现象**：发现某个参数没有说明，就判定它不合理、建议下调。

> **判据**：参数通常**服务于某个结构**。改参数前先找出它服务的结构——
> ```
> 发现"参数可疑" → 先找它服务的结构 →
>   矛盾在结构（字段数 × 输入量错配）→ 改结构，不是改参数
>   矛盾真在参数 → 用实测数字改，不用推测改
> ```

### 2.4 注释与可观测状态冲突时，以可观测状态为准

> **判据**：注释是意图，配置是事实。冲突时以可观测状态为准，并回头修注释。引用他人注释/旧结论时，**找机会验证它是否仍成立**——转述忠实 ≠ 内容正确。

### 2.5 基线假设必须每轮校验

**现象**：上一轮正确的前提，这一轮已经变了（代码改了、数据更新了、外部推进了）。

> **判据**：把"曾经核实过"当永久有效，是隐性技术债。关键前提**每轮重新校验**，尤其是三类：**数据源在哪 / 某功能是否已实现 / 当前处于哪个阶段**。

### 2.6 外部事实当场标来源；配额与限流查官方一手

> **判据**：引用外部事实时当场标注来源与核实时间（没有来源的事实 = 记忆，记忆会漂移）。涉及**配额、限制、价格**的，必须查官方一手来源——二手来源（含已停维护的仓库）常是错的。

### 2.7 转述实测数字要保留原始形态

**现象**：把"首跑 ¥0.06–0.08 + 二跑 ¥0.16"说成"总共约 ¥0.2"，区间被压成点值，误差信息丢失。

> **判据**：保留原始形态（区间、计数、分母）；多个来源的数字**分别列出，不合并**；确需汇总时标注是"估算"还是"实测"。**说比例必须说分母**——同一指标 4% 与 76.7% 都对，因为分母不同。

### 2.8 待办清单有保质期

**现象**：按一份旧清单执行清理，其中两项（死代码、迁移漂移）实际根本不存在。

> **判据**：对**删除类 / 迁移类 / 不可逆类**待办，执行前先验证目标仍存在。不存在 → 报告"无，无需处理"，不为完成 KPI 硬做。

### 2.9 示例块 ≠ 真实配置

> **判据**：示例与真实配置同处一份文档时，**明确标注哪份是示例**。改配置前先确认改的是生效的那一份。

### 2.10 校验要对着数据的权威源做，不是最顺手的那个

> **判据**：用本地副本校验 id 是否存在，而本地库是过期快照 → 最新条目永远校验失败。校验对象必须是**权威来源**，不是"最容易连上的那个"。

### 2.11 改文档前必须通读，不能只 grep 锚点

> **判据**：grep 只能定位，不能证明"别处没有"。改任何规范类文档前**通读全文**，交付前**逐节通读、表格逐行看**（§11.10）。

### 2.12 ★ 先拿证据再改：一步区分"截断 / 格式错误 / 逻辑错误"

**现象**：输出解析失败，三种原因的修法完全不同，但表现相似。

> **判据**：最小代价的区分方法——打印原始输出的**长度 + 前 500 字符**：
> ```
> 长度 = 上限值，且在句子中途截断   → 截断（调大上限）
> 长度正常，但结构不对             → 格式错误（改解析/改 prompt）
> 输出为空                         → 上游就没生成（可能是重试也吃满）
> ```
> **没有这一步，后面全是猜**——而猜错方向会浪费好几轮。

### 2.13 诊断环境必须与真实环境一致

| 反模式 | 后果 |
|---|---|
| 用本地数据库诊断线上问题 | 本地库可能是几周前的快照，**结论完全不可用** |
| 用"网络不通"推断"源不可用" | 可能是本机 DNS/代理问题，线上正常 |
| 复用旧数据目录 | 掩盖"全新环境缺目录 / 缺初始化"类问题 |

> **判据**：诊断前先问"**我看到的这份数据，能代表真实运行状态吗？**"

### 2.14 修复的连锁效应：改了规模必须回归

**实例**：把时间窗口从 7 小时修成 24 小时（正确修复）→ 条目从 1 条涨到 174 条 → 输入膨胀约 10 倍 → 撞上 token 上限 → **另一个模块从正常变成完全失效**。

> **判据**：改动涉及规模时，问一遍——
> - [ ] 输入长度会变吗？有没有 token / 缓冲区 / 分页上限？
> - [ ] 处理时间会变吗？有没有超时？
> - [ ] 存储会变吗？有没有配额？
> - [ ] 之前"没暴露"的问题，是不是只是因为规模小？
>
> **"实测没暴露" ≠ "不存在"，只说明触发条件还没到。**

## 3. 推断的边界

### 3.1 前提正确 ≠ 结论正确

**现象**：从"两天采集失败"推出"从那天起一直失败、该功能从未产出过数据"。

> **判据**：**推论每跨一步，问一次"这一步有没有实测支撑"**。没有 → 标注为待核实，不写成确定结论。证据覆盖的范围就是结论允许的范围。

### 3.2 空白不是证据

> **判据**：未核实的区域保持空白或标"待核实"，不要把"未验证"写成确定的坏消息，更不要升格为阻塞项。

### 3.3 方向对 ≠ 机制对

**现象**：判断"这里有问题需要挡住"，但把成因猜错了；做了修正后指标完全没变。

> **判据**：做修正时同时验证两件事——① 修正后指标是否如预期变化；② 若未变化，**如实报告并重新归因**。不要把"做了修正"当成"解决了问题"。

### 3.4 自己推翻自己，要主动说

> **判据**：发现上轮判断有误时写清"我上轮说的是 X，那是错的，因为 Y"。悄悄改掉比说错更糟——别人无法判断哪一轮可信。

### 3.5 ★ 论证越完整，越要找反例

> **判据**：说完一个方案后强制问："有什么是它没覆盖的？"听起来无懈可击的论证，恰恰说明它掩盖了什么。

### 3.6 撤回过的结论进禁区

> **判据**：同一对象再次涉及时**强制重读原文**。这一条被违反过——撤回后下一轮立刻重犯。

### 3.7 分层统计，绝不混合报告

**现象**：召回率 29%，但其中没有一项是"规则实现了却没查出来"——真正该做的是实现规则，不是改规则。

> **判据**：任何准确率/召回率报告都要**分层**（规则范围内 / 规则未实现 / 无规则 / 基线存疑），明确写出哪些没进分母、为什么，每层单独给结论，不给笼统总数。

### 3.8 命名决定结论

**现象**："工具报了但基线没有"未必是误报，可能是真问题而基线漏了；叫"误报率"会让人不去查。

> **判据**：命名前先问"这个名字会不会让人停止追查？"不确定的分类用**中性词**（unmatched / pending / unknown），不用贬义词（error / false），并留人工复核的口子。

### 3.9 估算必须拆成「单位 × 频次」

**现象**：实测单条 78 B（很准），但漏了采样频次（每篇每年 4 次），结果低估 2.6 倍。

> **判据**：`总量 = 单位大小 × 数量 × 频次`——**频次最容易漏**。三个因子缺任何一个就不算估完。

### 3.10 用敏感性分析找真杠杆

**现象**：以为预筛通过率是最大杠杆，把它推到极端值后总量几乎没变——因为它只影响"多少对象"，而单对象成本本来就极低。

> **判据**：对候选杠杆推到极端（0 和 1）看结果变多少，变化小就不是杠杆。

## 4. 建模优先于编码

### 4.1 建模错误的特点

> **它能通过所有测试，只是结果不对。** 代码错误会崩溃、会报错、测试会红；建模错误安静地产生"看起来合理但语义错误"的结果。**建模错误比代码错误贵 10 倍。**

### 4.2 时间语义三态

| 语义 | 依据 | 适用 |
|---|---|---|
| **事件（event）** | 发生时间 | 有准确时间戳，且**产生即可见** |
| **状态（state）** | 最后观测时间 | **没有发布时间**，只关心"当前是否成立" |
| **发现（discovery）** | 首次观测时间 | 有发布时间但存在**索引/同步滞后** |

> **判据**：用"发生时间"的前提是 **发生时间 ≈ 你能看到它的时间**。**只要存在滞后，就必须改用首次观测时间。**
> 反例警示：为滞后源配了 7 天回抓，过滤时却只保留 24 小时内发布的——**抓了却不用，等于白抓**。

### 4.3 两个时钟不混用

> **判据**：一个对象有多个时间语义时（成熟度用发布时间、观测窗口用首次发现时间），**显式命名并写死用途**。混用会导致"全量复活 / 状态错乱"。

### 4.4 身份指纹 vs 观测值

**现象**：`content_hash` 含引用数 → 引用数从 3 变 5 → hash 变了 → 系统当成新对象重新入库、覆盖用户数据。

> **判据**：**身份证号不随体重变。** 只要用哈希做身份或缓存键，先问"这里有没有会随时间变的字段"，有就排除。

### 4.5 ★ 把数据分成「可再生」与「不可再生」

| 类别 | 特征 | 该付的成本 |
|---|---|---|
| **可再生** | 从源重采即回 | 放可丢弃缓存，**不持久化** |
| **不可再生** | 丢了就是真丢 | 必须持久化 + 备份 |

> **判据**：只为不可再生数据付持久化成本。把"能重采"当成"零成本重采"是错的（重采要时间、要配额），但它仍不足以支撑持久化，只影响"多久能恢复"。
> **典型不可再生数据**：首次见到某对象的时间、时序快照、判断记录、用户笔记。

### 4.6 累积量的两个陷阱

> **判据**：① 累积量没有下降 ≠ 没有流失（新增可能正好抵消流失）；② **不能从存量差分反推日增**。需要增量就单独记录。
> 读取历史累积数据时**按最老格式做容错**（缺字段给默认值、类型不一致做转换），解析失败要报出来，不能静默跳过。

### 4.7 ★ 层次不能混用：意图层 / 入口层 / 评估层

| 层 | 职责 | 允许的判断 |
|---|---|---|
| **入口层** | 决定"什么进系统" | 只做**客观事实**判断 |
| **意图层** | 决定"我关注什么" | 只做**标记与排序** |
| **评估层** | 决定"它好不好" | 可以做主观判断 |

> **判据**：每一条规则先问"它属于哪一层"，越界就是 bug。**意图层尤其危险——它长得像过滤器，但不是。**
> 三次踩中：把定级硬约束搬进 watchlist（系统性误杀）、拿 watchlist 当领域过滤器（关联图只剩我看过的方向）、拿预筛决定是否入库。

### 4.8 关系建模的三条

> **判据**：
> ① **对称关系只存一条**，渲染时双向展开（否则双倍行数 + 两套真相）；
> ② **关系型数据必须有方向验证测试**（有向边、父子、上下游），写反了所有单测都会通过；
> ③ 合并重复实体时，想清楚保留哪个时间、**哪些字段该更新、哪些不该**（踩过的坑：保留了首次发现时间，却忘了同步更新"最后观测时间"，导致持续存在的数据被判为过期）。

### 4.9 主键 / 聚合键先数覆盖率

> **判据**：设计聚合键、主键、关联字段前先数覆盖率。10% 覆盖的字段当主键 = 90% 数据无处安放。**聚合维度：稳定 > 精细**——宁用稳定的粗维度（全覆盖），也不用不稳定的细维度（天天变、累积落空）。

### 4.10 连续量别离散化成档

**现象**：为省一点成本把"增强多少条"做成三个档位，配置组合从 3 变成 9。

> **判据**：如果一个量本来就是连续的，就别发明"档位"这个概念。直接暴露成数字（`enhance_top_n: 20`），实现从分支变成循环上限。

## 5. 数据质量：缺陷会伪装成趋势

### 5.1 核心模式

**同一项目复现三次**：

| # | 真实情况 | 被读成的结论 |
|---|---|---|
| 1 | 榜单每天换血 70%，66% 条目只出现 1 天 | "XX 话题已消失"（实为跌出榜单） |
| 2 | 某天采集失败，该板块 0 条 | "前高后低的结构性回落" |
| 3 | 中途新增两个数据源 | "该板块暴涨 22.8%"（同构区间实为 +2.77%，**方向反转**） |

> **数据缺陷不会消失，它只会变形。** 堵住一个入口，它会从另一个入口冒出来。

### 5.2 ★ 归因是数据的属性，不是某个结构的属性

**错误做法**：发现某模块会被污染 → 只在该模块剔除 → 同样的污染从斜率、来源份额等别的入口再次出现。

> **判据**：只要某份数据被判定为不可信，**所有用到它的计算都必须传播这个判定——无一例外**。

| 情形 | 处理 |
|---|---|
| 坏日（夹在两次有数据之间的 0 值） | `masked`：既不累计也不中断连续段 |
| 整源失败（整源 0 条） | 该板块/来源 `usable=False`，**封锁所有趋势判断** |
| 口径变更（源集合变化） | 见 §5.3 |

### 5.3 分段可比性，而非整块废弃

> **判据**：一刀切废弃会用"过度保守"换掉"过度声称"，等于换个方向的失真。正确做法：① 标记变更点；② **跨**变更点的比较禁止；③ 变更点**之后**的同构区间允许；④ 段长低于最小阈值不作判断（防止把长窗口切太碎）。

### 5.4 禁止用"填补"掩盖采集失败

> **红线**：采集失败时**禁止复用上一次的缓存数据填充**——那会让过期数据伪装成新鲜数据。正确行为是**归零 + 让故障可见**（告警、横幅、健康检查）。

### 5.5 数据质量决定质量上限，不是 prompt

> **判据**：反复优化 prompt 而产出质量不达标时，先检查**输入的数据量与健康度**。数据不够或不干净时，prompt 迭代的边际收益趋近于零。不必过度优化 prompt，让数据自然累积。

### 5.6 为每个外部依赖做独立健康监控

**现象**：某数据源持续失败，但被另一个恢复的源顶上，整体看起来正常 → 故障被掩盖多天。

> **判据**：**聚合健康 ≠ 各组分健康**。不要只看聚合结果。

### 5.7 自动化会放大既有缺陷

> **判据**：**在接入自动化之前**，先确认该流程的产出量在长期可承受。手动时的"小毛病"（每天多产 20 条），自动化后变成"每天累积的灾难"（7300 条/年）。

### 5.8 先找"唯一副本"

> **判据**：每个项目先问"**什么东西丢了就真丢了？**"通常只有一个，而且不是你以为的那个（往往是无备份的用户数据/笔记）。找出来，优先给它备份。

## 6. ★ 静默失败治理（最重要的一章）

### 6.1 问题的本质

有一类缺陷**不抛异常、不崩溃、退出码为 0、所有测试通过**，但功能实际没生效：

| 类型 | 表现 |
|---|---|
| 静默降级 | 走了降级分支，产出为空但流程正常 |
| 静默失效的配置 | 配置写了但没被读取，或优先级被压制 |
| 静默滑出窗口的数据 | 被过滤条件静默排除 |
| 静默命中的错误缓存 | 缓存键缺维度，返回错误结果 |
| 注册了但从不生效 | 规则/钩子写完了，但从没真正命中过（见 §7.3） |

> **共同点：系统"看起来正常"，直到某天你发现某个功能其实一直是空的。**

**为什么常规手段抓不到**：测试断言的是"流程跑通"不是"功能真的生效"；日志里有 `degraded: true` 但没人看；没有异常，无从告警。

### 6.2 应对原则：把关键状态从"日志"提到"产物"

| 手段 | 做法 |
|---|---|
| **状态进产物** | 降级标记、跳过原因写进输出文件的元信息 |
| **结果可核验** | 生成物附"对照表"，让人工能抽查 |
| **产物可 diff** | 每次运行产出并版本化——**异常往往藏在"今天和昨天不一样"里** |
| **空态显式化** | "无数据"要输出完整结构并标注，而非静默省略 |

> **宁可显眼地失败，也不要安静地成功。**

### 6.3 ★ 加「跳过」逻辑前，先问一句话

**现象**：往脚本里加"条件不满足就跳过并记日志"看起来是保护，实际把**必然失败**变成**必然静默跳过**。

> **判据**：加任何「跳过」逻辑前，问「**这个条件会不会长期为真**」。会 → 这不是保护，是让功能永久失效。

### 6.4 自己加的东西会破坏自己加的自动化（复现三次）

1. 日报产物污染工作区 → 定时脚本的脏树检查命中 → 静默跳过导出
2. 日志目录未排除 → 同上
3. 新增产物类型入库 → 本地重跑必然脏树 → 定时任务跳过

> **判据**：每次新增"会产生文件 / 改变状态"的功能，回头检查一遍**所有依赖"干净环境"的自动化脚本**。

### 6.5 退出码分级（要显式转换，否则形同虚设）

| 码 | 含义 | 处理 |
|---|---|---|
| `0` | 正常（**含"跳过"**） | 继续 |
| `1` | 质量不达标 | 转为 warning，**继续** |
| `≥2` | 用法错误 / 真错误 | 保持非 0，标红 |

> ⚠️ 多数 CI 中 step 非 0 **默认标红**，不会自动变 warning。**必须显式捕获退出码并转换**。
> 配套：**"可选功能失败"不应影响退出码**，但要让它可见，否则等于假装没发生。

### 6.6 让"干净状态"成为有效信号

> **判据**：频繁自动变化的产物**不要纳入版本控制**。否则仓库永远脏 → 你会习惯性忽略 → 真正该关注的变化（如用户笔记变动）反而看不出来。

### 6.7 检查清单

- [ ] 每个降级分支是否都记录了原因？
- [ ] 降级标记是否出现在**用户会看的地方**，而不只是日志？
- [ ] 有没有"空结果"和"功能失效"无法区分的情况？
- [ ] 产物是否可 diff（版本化 + 结构稳定）？
- [ ] **有没有哪个功能"没人确认过它真的产出过非空内容"？**（最后一条最有效，能抓出大部分静默失败）

## 7. 测试、验证与评估

### 7.1 ★ 写测试前先问：这条断言在什么情况下会恒真？

**四次踩中**：

| 场景 | 表象 |
|---|---|
| `assert "★" in output` | 脚注说明文字也含 ★ ⇒ 恒真 |
| 路径泄露扫描 | 配置文件**注释**里写了反例 ⇒ 被自己的测试误伤 |
| 作者归一化 | 只处理 `J. Doe`，漏了 `DOE, John` ⇒ 同一实体两个键 |
| 跨天幂等 | 比较时含换行 ⇒ **当天全绿、隔天才暴露** |

> **判据**：断言必须针对**真实输出结构**，不做全文 `in` 匹配。写完就问：这条断言有没有可能**永远为真**？有没有可能**永远为假**？
> （上例修正为：断言"表格行以 ★ 开头"。）

### 7.2 配反向断言，防止"恒等函数假绿"

> **判据**：只测"不该变的不变"，一个永远返回常量的函数也能通过。任何"过滤/排除"逻辑都要配一条**"该命中的必须命中"**的测试。

### 7.3 ★ 每个检查点配一个"故意让它失败"的用例

**"注册了但从不生效"在同一项目踩了五次**：

| # | 问题 | 后果 |
|---|---|---|
| 1 | `raise NotImplementedError` 无括号时 AST 是 `Name` 不是 `Call` | 规则从不命中 |
| 2 | 方法节点没有 `bases`，基类在 `ClassDef` 上 | 豁免永远失效 |
| 3 | `pytestmark = ...` 是 `Assign` 不是 `Expr` | 规则从不命中 |
| 4 | 依赖表缺别名解析 | 检查点形同虚设 |
| 5 | `str.replace` 用 `"message":` 匹配 `message=` | 静默没匹配上 |

> **判据**：只测通过测不出失效。① 每加一个检查点/断言/钩子，立刻写对应的失败用例；② 断言**命中数 > 0**，不只断言"没报错"；③ 字符串/正则替换后**必须校验计数**。
> 这类缺陷比"漏掉一条规则"严重得多——漏了看得见，注册不生效是隐性的。**同类问题第二次出现就该写进工程规矩，不要等第三次。**

### 7.4 反向测试比正向测试更能暴露质量

> **判据**：拿一个"应该报 0 条"的**健康对象**做测试，报出的每条都逐条看——报出真问题是意外收获，报出误报正是要找的，报 0 条只证明"不吵"（必要不充分）。
> **正例只能证明"规则能命中"，误报才能证明"规则想错了"。** 而且反向目标永远可得（工具自己就是个健康对象）。

### 7.5 从误报反推设计缺陷，而不是调参压掉它

| 只给现象（会被怎么修） | 给根因（实际怎么修） |
|---|---|
| 报了 33 条 → 收紧阈值 | 该用兄弟解析 → 加解析模式 |
| 报了 → 去掉那 4 个 pattern | pattern 应分级 → 核心/可选两层 |
| 报了 → 排除那个文件 | 应剥离代码块 → 加护栏 |
| 降级了 → 提升严重度 | 它是整文件型 → 加入豁免清单 |

> **判据**：误报来了先假设"我的模型错了"，不是"数据脏了"。修误报时问：这是不是一类问题？能否提炼成机制？记录**根因分类**，不只是修掉它。
> **纠错指令必须给根因**——只给现象，实现方会打补丁；给根因，它才会改设计。

### 7.6 时间驱动逻辑必须跨周期测试

> **判据**：涉及时间推进的逻辑（过期、重试、状态流转、缓存失效），必须写**受控时钟下的跨周期测试**，不能只测"当天"。

### 7.7 不伪造 fixtures

> **判据**：拿不到真实响应就 `pytest.skip(reason=...)` 并写明原因。**用假数据测出来的"通过"比 skip 更危险**。

### 7.8 环境相关断言要隔离

> **判据**：测试对环境的假设要显式（CI 无 key / 本地有 key），用 env 隔离，不让环境差异伪装成回归。

### 7.9 确认"真的跑了"，不看 exit code

**现象**：mark 过滤导致静默选 0 个用例，测试"通过"但什么都没跑。

> **判据**：验收时确认**用例数**，不只看退出码。

### 7.10 阈值必须实测后定，不预设

**现象**：预设"绝对误差 < 1e-5"，实测发现 fp32 物理上达不到（噪声地板 1.6e-4）→ 不可达的阈值只产生假失败，逼你去"修"不存在的 bug。

> **判据**：① 先打印实测数据（含量级 `max|ref|`）；② 据此定阈值（用相对误差）；③ 记录余量倍数，标出余量最小的那个。

### 7.11 区分"真 bug"和"精度问题"的统计判据

> **判据**：归一化后的相对误差——**逻辑错误**会参差不齐、量级跳跃；**浮点噪声**会整齐落在同一个窄带里。这比单看阈值更有说服力。

### 7.12 没有评估的生成类功能等于没做

**四层评估框架**：

| 层 | 检测什么 | 防什么 |
|---|---|---|
| **L1 硬判据** | 格式、长度、禁用词、结构完整 | 形式缺陷 |
| **L2 信息增量** | 与基线对比，统计**输入中不存在的结论**数 | **"重述即通过"** ⭐ |
| **L3 跨期回检** | 上期的判断本期是否成立 | 说了不算 |
| **L4 校准追踪** | 上期结论的延续率 → **反馈收紧下期准入门槛** | 过度声称 |

> ⭐ **L2 是唯一能抓"正确的废话"的一层**：有锚定、有数字、但没有任何输入里没有的信息——形式检查全过，实际零增量。

### 7.13 检验对象必须是被检验的东西本身

**现象**：想检验"关于**结构**的判断"，却去统计"**条目**的存活率"。板块份额上升，不代表它引用的代表条目必须在榜。

> **判据**：**用代理指标检验，等于没检验。**

### 7.14 前置门：样本不足时判 insufficient，不判 fail

> **判据**：设前置条件（最小时间间隔、最小样本量），不满足时返回 `insufficient`：记录该次观测（**不丢弃**）、**不**触发失败判定、**不**据此调整后续策略。

### 7.15 反馈闭环：检测之后必须能改变行为

> **判据**：设计检测层时同步问"检测到问题后系统会自动做什么？"答不上来就是没闭环。只有检测没有反馈 = 报了也没用。

### 7.16 ★ 证伪 / 验收条件必须可判定

**现象**：条件是"仍在前 30 **且**热度 ≥ 82.89 → 证伪；跌出 **或** 热度 < 82.06 → 维持"，实际值 82.82 落在两者之间 → 两个分支都不触发，**判定悬空**。

> **判据**：任何用来判定成败的条件必须**可观测、互斥且穷尽**。
> ❌ 禁止用**点值区间**构造分支（必然留灰色地带）
> ❌ 禁止用**合取**连接两个独立观测（组合态 4 种而分支只有 2 个，必然覆盖不全）
> ✅ 用**单一可观测问句**："X 是否仍在 Top30"
> 配套：改判据时同步改生成它的 prompt，否则只是"检测到了再判失败"，下次照样生成。

### 7.17 先建度量，再建功能

> **判据**：如果不知道当前方案抓到了多少、漏了多少，就不要开始优化它。度量模块与功能模块同等地位，不是附属品。哪怕基线很粗糙，先有再迭代。

### 7.18 显式声明"不覆盖什么"

> **判据**：任何检测/分析类产出必须显式声明边界，且声明**无条件输出**（曾因依赖启发式条件而被自己的夹具吞掉）、放在**开头**（末尾没人看）。
> 理由：**静默跳过会让用户误以为"没报问题就是没问题"**——这恰恰是这类工具要解决的毛病。

### 7.19 母规则抑制要显式声明

> **判据**：当规则 A 命中会导致 B 必然命中时，显式声明抑制关系，让 B 合并计一条（**抑制 ≠ 丢失信息**，被抑制的子规则仍以"N 个"的形式出现在母规则描述里）。新增规则时强制回答"它有没有母规则"。

### 7.20 结构保证 > 承诺

> **判据**：重要约束要做成"**代码里不存在这个能力**"，不是"文档里写了不要这么做"。遇到"要提醒别做 X"，先问能不能让 X **编译不过 / 调不到**（如扫描链路只导出读 API、唯一写入口单一职责）。权限按最小集暴露，不按"全给 + 提醒别用"。并用测试锁住结构保证。

### 7.21 可证伪性由代码判定，不由人 / LLM 判定

> **判据**：评估类系统里，**"样本不足 / 不可证伪"要显式排除在统计分母之外**（另存，不假装有了结论）。让模型或评审者自己判断"我这条能不能被证伪"等于没判断。

### 7.22 核心机制先做早期小规模验证

**实例**：引用边上线后才测得命中率 0.0095%，差点让整个关联层白做。

> **判据**：对**核心机制**做早期小规模验证（如 200 篇跑一次看产出量），确认量级合理再全量铺开。
> **别让"快完成了"掩盖"方向错了"**——越接近完成，越舍不得做这个验证，而它恰恰最便宜。

### 7.23 自举验证：让工具审它自己

> **判据**：每完成一组能力，拿**正在做的这个项目本身**当测试目标跑一遍。三条理由：
> ① **测试目标永远可得**——不需要额外构造，自己的项目天然是最熟悉的健康样本；
> ② **它抓到自己的问题是最有力的演示**（实例：自审计抓到自家仓库里 3 个被跟踪的 `.pyc`，带出关键判断"事后补 `.gitignore` 不会让已跟踪文件自动消失"——比十行设计论述都有说服力）；
> ③ **它能发现你自己的疏漏**。
> 把"跑一遍自审计"固化成流程步骤，且**不要因为"这是我自己的项目"就手下留情**。

## 8. LLM 应用工程

### 8.1 先划边界：什么该算，什么该生成

**实证**：让模型自主挑选"哪些条目重要" → 覆盖率崩到 4%；让模型自己"发现趋势" → 它只会复述最显眼的那个。

> **判据**：**模型的强项是解释与判断，不是筛选与计算。**

| 交给代码 | 交给模型 |
|---|---|
| 跨期聚合、变化量、排序、聚类 | 解释这些结构意味着什么 |
| 可复现、可单测、零成本的部分 | 推测、权衡、指出矛盾 |

### 8.2 绝不回显输入

**事故**：把输入原文回显给模型 → 输出膨胀约 10 倍 → 撞 token 上限 → **生成 0 条**。

> **判据**：证据包**只给结构化摘要**（id + 标题 + 数值 + 分类），**绝不回显正文**；同时验证输出里不含输入原文。
> 推广：**输出也要紧凑**——只让模型返回必要字段，不要它回显输入。理由不只是省钱，回显会让输出翻倍直接撞上限，导致本该成功的调用失败。

### 8.3 有检测还要有预防

**现象**：发现输出里有合取式证伪条件，补了校验器去抓，但 prompt 没改 → 模型不知道这条规则 → 重跑写出同样的问题。

> **判据**：**只加检测不加预防，等于花钱买一个已知结果。** 每次新增一条校验规则，同步问："模型知道这条规则吗？"不知道就写进 prompt。

### 8.4 不要给模型留模糊退路

> **判据**：任何"不确定/无法判断"的选项，**只能由系统按硬条件产生，不能让模型自己选**。一旦允许模型输出"无法判断"，它会把它当成逃避困难判断的软出口，导致质量指标被系统性美化。
> 配套：硬条件在代码里判定（如证据条数是否达标）；模型只能在给定有限集合里选；"拿不准"不等于中间值，应走系统的重试或跳过路径。

### 8.5 结构化输出要有万能兜底

> **判据**：降级阶梯必须以**纯文本**结尾：`强约束格式 → 弱约束格式 → 无约束（schema 内嵌 prompt + 文本解析）`。前两级都可能不被支持（模型/版本差异大），只有纯文本是所有模型都支持的。
> 配套：降级状态按 **（模型, 格式）** 记忆，**不能全局布尔**（否则 A 模型的失败会连坐 B 模型）；重试次数有限，超限**降级返回空而非抛异常**；推理型模型输出更长，超时上限要分层。

### 8.6 防幻觉：预防 + 校验 + 可核验

| 层 | 做法 |
|---|---|
| **输入** | 只给可核查的信息，不给猜测空间 |
| **Prompt** | 把允许的取值集合注入，要求"只能从中选择，不得构造"；无数据就固定输出"待观察"，明令禁止"可能/有望"填充 |
| **校验** | 检查输出是否在集合内，不在则重试一次，仍失败则丢弃 |
| **可核验** | **在产物里输出对照表**，让人工能抽查 |

> 最后一层最容易被忽略，但它把"一次性验证"变成**常态化能力**。前三层不可能 100% 有效，**必须让残留问题可被发现**。

### 8.7 ★ 防幻觉与可读性不是对立的（双层呈现）

> **判据**：专业的、结构化的、高信息密度的数据应该保留；给人看的必须符合人类阅读习惯。两层**都保留、分层呈现**，不取舍。

| 层 | 内容 | 载体 | 给谁 |
|---|---|---|---|
| 专业数据层 | id / 数字 / 免责 / 口径 | JSON、文末溯源区、折叠块 | 机器校验 / 想深挖的人 |
| 人类阅读层 | 结论 / 图表 / 重点 / 视觉符号 | 正文 | 人 |

> **红线**：不得为了排版好看删掉自动校验依赖的数据。信息密度不降低，只是移到不阻塞阅读的位置。
> **反面教训**：把"防幻觉"做成"让模型展示工作过程"——要求每条结论锚定 id + 数字 → 满屏裸 ID；要求禁说"消失" → 免责声明泛滥。

### 8.8 不合成单一分数；主观判断必须锚定

> **判据**：① 明确不输出单一综合分，客观信号与模型判断**分列**——综合分会把模型的不确定性藏起来；② 凡要模型做**定性判断**的字段，都要指定"依据必须来自哪里"（引用可核查事实），无据则输出"待定"。不给依据来源，模型就会编。

### 8.9 条件式降级 > 一刀切砍功能

> **判据**：数据不足时，降级"这个字段的输出"（有数据就输出并附出处，没有就留空并说明），不要砍掉"这个功能"。

### 8.10 判废不依赖模型回显；连续失败即熔断

> **判据**：① 校验 LLM 输出用**结构化解析 + 内容校验**，不要求模型复述你给的标记（被截断的输出会被误诊为"不听话" → 重复付费）；② 任何外部依赖设连续失败上限，到点中止本轮并留痕——同一类失败重试只会烧钱，通常是系统性原因。

### 8.11 max_tokens 是上限不是目标

> **判据**：调高它不会让模型写得更多，但能消除截断风险；按实际 token 计费，调高无成本风险。**必须有截断检测**（`finish_reason == length` → 抛错或标记），否则会静默返回半截文本——全仓曾出现 0 次检测，截断永远不被发现，只表现为"输出变短/解析失败"。

### 8.12 按「任务难度 × 调用频率」分档选型

> **判据**：高频轻量用快模型，重分析用强模型，不让强模型干简单活（烧钱且慢）。
> **★ 真正该省的是轮次，不是档位**：用弱模型磨 5 轮 ≈ 用强模型 1 轮——成本相近，但后者质量更高、你花的时间更少。
> 升档信号：同一问题连续 2 轮没解决 / 输出开始顾左右而言他 / 产出明显逻辑混乱。

### 8.13 能真跑就别桩跑

> **判据**：桩只证明代码路径通，不证明真实输出质量。涉及 LLM 输出质量的功能**必须至少真跑一次**（成本是障碍就真跑一次，而不是只跑桩）。

### 8.14 输入分布决定输出的分歧空间

**现象**：多角色辩论中证据包 15 条有 14 条来自同一类别 → 四个角色的分歧全挤在同一个维度。

> **判据**：想让多方讨论产生真实交锋，先保证**证据包覆盖多个维度**。输入偏斜会把输出的丰富度锁死。

### 8.15 两条反直觉

| 观察 | 含义 |
|---|---|
| **最好的段落最短，最差的段落最长** | 字数多 ≠ 质量高。要求写很长，本身就在逼注水 |
| **讲限制比讲结论更占篇幅** | 诚实说明"为什么某部分不可用"比罗列结论更费字。**这是正确代价，不要为压缩篇幅删掉它** |

### 8.16 外部能力先实测再接线

> **判据**：接第三方数据源前先实测真实响应。伪装成正文的回退（如把 HTML 错误页当正文返回）**比返回 None 更糟**，宁可 fail-closed。

### 8.17 延迟决策

> **判据**：定级/分类这类需要富集数据的事，**先入库后判定**（等引用数据成熟再调用模型）。大部分对象永远攒不到有意义的数据 ⇒ 根本不需要定级。成本降了，质量反而升了。
> 推广：**"少做"也可以是优化**——优化昂贵调用时，先看**触发条件**，再看调用本身。"这条请求该不该发"通常比"怎么发更省"更省。

### 8.18 省钱的优先级（按性价比排序）

1. **结果持久化**（不做的话成本随规模线性增长，**且同一输入会反复产出不同结果**）
2. **缩小作用范围**（只对必要部分做）
3. **按条件跳过**（已满足的就不做）
4. **降低质量档位** ← **最不推荐，它削减的是价值而非浪费**

> **省钱的杠杆是减少不必要的调用，不是降低输出质量。** 缓存命中率通常比单价差一个数量级（决定性杠杆）；**预算闸门的定位是防失控，不是省日常**——设成"能容纳单日全量、但容不下失控"，真出问题时第一天就暴露。

### 8.19 成本可观测先于优化

> **判据**：先有 `cost` 命令 + 异常告警，再谈降本；改"每天必跑"的参数先算 `日 × 365`。涉及调用计费的功能，**实测一次成本并记录下来**（预估容易偏差一个量级）。

### 8.20 严禁编造，引用守界

> **判据**：无证据的结论**留空并标注**，绝不让模型补全它不知道的内容。凡涉及外部事实 / 版权：
> **数字可自由引用、文字优先改写、图表重画不复制**，引用标出处。

## 9. 架构、依赖与外部集成

### 9.1 选依赖：可测试性优先于"官方"

**实例**：官方 SDK 带来自己的 HTTP 客户端版本，导致既有 mock 工具失效 → 该模块覆盖率 0%，而后续逻辑强依赖 mock。改为直连（60 行）后覆盖率 94%。

> **判据**：把"它对测试能力的影响"作为**一票否决项**。
> - [ ] 它会不会让我现有的 mock/测试工具失效？
> - [ ] 它的抽象层会不会让错误定位变难？
> - [ ] 它提供的能力我是不是已经有了？（重复的通常该去掉）
> - [ ] 传递依赖有多少？

**不等于"什么都自己写**：**链路固定 → 自研可控；链路需要动态编排 → 用框架。

### 9.2 单一职责 + 唯一出口；横切能力收敛；编排层是唯一事务边界

> **判据**：① 网络、配置、存储、日志、时间这类横切能力各收敛到一个模块（测试可对其断言，如 off 档 0 请求）；② pipeline 负责事务、隔离、汇总，下层只做纯函数式产出——**错误在协调者处归一**（把降级塞进执行者会外泄成非零退出码，整条流水线崩）。

### 9.3 单向数据流优于双向同步

> **判据**：双向同步的复杂度是单向的平方级。能做成**单向物化视图 + 受控回流**（回流部分用标记块保护），就不要做双向。
> 例外：**自动化写入 + 人工写入共写一个远端**时，提交前必须 **fetch/rebase 并对齐差异**——否则会用缺数据的树覆盖真源。

### 9.4 决策点外置；死配置要么接线要么删

> **判据**：所有"可能要调、要审计、随环境变"的参数外置为声明式配置（环境差异用 `${ENV}` 占位符而非分支），代码内不写死阈值（写死会被同名配置压掉，且运维无法不重启调整）。
> **留着不接线的配置/开关，要么接上消费者，要么注释写明"谁将来消费"，否则删**——"看起来已实现"的假象比没有更糟。

### 9.5 YAGNI 的正确用法

> **判据**：✅ 该用——没有具体场景的"将来可能需要"；❌ 不该用——已经踩过坑、明确知道会出问题的地方。
> 问"我现在有这个场景吗？" vs "我见过它出问题吗？"
> **不为想象中的将来写抽象，但为已识别的变更点留一个最小接缝**（一层接口，不搞 Registry、不做插件发现）。

### 9.6 外部接口五条

> **判据**：
> ① **批量接口优先，禁止逐条**——逐条调用会把请求数放大 N 倍，这通常是限流的真正原因；
> ② **网络可达性 ≠ 源的可用性**——`availability` 描述的是源本身是否公开可用，不是"从我这台机器能不能访问"。不可达时 warning + 跳过、**不计失败**，并提供 `base_url` 让用户填镜像（把一次网络波动固化成永久功能缺失是错的）；
> ③ **N+1 与回采要算总量**——引入"对每条 X 再拉 Y"前，先乘日增量看年量级；跨表关联**先分桶，禁全量两两比较**（23 万篇两两 = 264 亿对直接崩）；
> ④ **单源失败不影响整体**——采集器互相隔离，失败记入降级字段、**退出码仍为 0**，但**降级状态必须写进产物**（不能只在日志里）；
> ⑤ **外部能力先实测再接线**——伪装成正文的回退（如把 HTML 错误页当正文返回）**比返回 None 更糟**，宁可 fail-closed。接之前先 curl 一下做**零成本连通性实测**，由实测结果决定通道，不猜。

### 9.7 幂等必须可断言，不能只靠"看起来没变"

**实例**：真 vault 不在版本控制里，`git diff` 检查不到它 ⇒ 幂等实际失去自动验证；tmp 目录里的测试是**替身**，不是真身。

> **判据**：每做一个幂等保证就问：**验证它的机制在真实环境下还在吗？** 不在就额外造一个（如 `export --check`：渲染后逐字节比对，输出"将要变更的文件列表"，退出码 0/1）。

### 9.8 文件内不留运行时间；用户数据区硬隔离

> **判据**：① 区分**内容时间**（数据变了才更新）与**运行时间**（程序跑过了）。把运行时间写进产物 ⇒ 每次运行都产生 diff ⇒ 真正的变更被噪音淹没（标记块注释内也不要放时间戳，极易漏）；
> ② 用户数据区用 `<!-- BEGIN/END -->` 标记块明确边界，只替换块内；配置文件**先读现有值 → 合并 → 写回**，绝不整体覆盖。

### 9.9 为「下一个消费者」设计产物

**反例**：导出条目列表而非合成文档，下游 AI 还要自己重新理解一遍。

> **判据**：任何产出都问一句"**半年后的我 / 另一个系统拿到它，能直接用吗？**"能则加分。产物要**自解释、可复用、可验证**，而非一次性输出。
> **真源 append-only，缓存可丢弃**：不可重建的事实（首次见到某物的时间、时序快照、判断记录）走 append-only 真源，对账靠 diff 不靠覆盖（§4.5）。

## 10. 自动化、git 与发布

### 10.1 本地过 ≠ CI 过（复现三次，原因各异）

- 测试断言 CLI 输出的某个字样，**终端宽度不同导致换行折断**
- 只跑了 lint 没跑 format check
- workflow 直到手动触发才发现边界问题

> **判据**：**自动化测试覆盖的是代码，不是运行环境。** 涉及定时、密钥、环境变量、并发、终端宽度的部分，**必须实跑验证**；推送后必须确认 CI 绿再继续。

### 10.2 脚本里 git pull 的三条硬约束

> **判据**：① 用 `--ff-only` 拒绝意外 merge；② pull 前确认工作区干净，失败即退出、不静默继续；③ **把"脏就跳过"显式写出来**，不要让它静默发生。

### 10.3 往既有脚本追加步骤前，先通读全文

**实例**：`daily`（写文件、污染工作区）与 `export`（要求干净才能 pull）前提互斥，却串在同一脚本里。

> **判据**：追加式修改前通读脚本全文，做**「副作用 × 前提」矩阵**，确认前面的步骤没有改变后面步骤依赖的状态（工作区、目录、变量、权限）。

### 10.4 设计冲突方案前，先确认自动化真的在运行

> **判据**：花力气设计互斥方案前，先确认双方是否真的在运行（`crontab -l` 实测为空 → 冲突链根本没发生过）。**没运行的东西不需要冲突方案。**

### 10.5 本地配置与 CI 配置是两套独立的面

> **判据**：改配置项时同步检查**所有部署面**（本地 `.env` / CI secret / 容器环境变量）。二者不一致不会报错，只会静默降级。注意 GitHub secrets **只写不读**，取不回本地。

### 10.6 并发写入共享远端要加锁

> **判据**：任何会写共享远端的定时任务，考虑并发互斥（如 CI 的 `concurrency`），否则并发 push 会互相覆盖真源。

### 10.7 提交拆分：一个 commit 一类改动

> **判据**：用 `git add -p` 按路径挑，不要 `git add -A`。`feat` / `fix` / `test` / `docs` / `chore` 分开——混在一起会让 `git bisect` 定位失效；也强制你思考"这改动到底是什么性质"，答不出来说明改动本身混杂了。
> 配套：**每步完成即 commit**（长任务每步先本地 commit 不 push，全部完成再一次性 push——任何一步可回退）；**`git init` 与 `.gitignore` 必须同时做**（先 init 后补 ignore 会把 `.pyc` 提交进去）。

### 10.8 查 git 事实用能返回数字的命令

```bash
git rev-list --count HEAD              # 提交总数（git log 输出会被终端截断，不要数行数）
git ls-files | grep -iE '\.(pt|pth|ckpt|safetensors|bin)$'
du -sh .git                            # 仓库大小，异常说明大文件进了历史
git check-ignore -v <file>             # gitignore 规则是否真生效
```

### 10.9 发布 / 转 public 前必查（不可逆）

> **判据**：`.git` 体积、有无大文件、有无密钥泄露（`git grep -iE 'api[_-]?key|token|password|secret'`）。**public 后才发现历史里有大文件，清理要重写历史 + 强推，代价极高。**

### 10.10 gitignore 的两个陷阱

> **判据**：① 每行只支持一个 pattern（`outputs/ runs/` 这类空格分隔**不生效**）；② **规则要看匹配范围**——`data/*.db` ≠ `*.db`，前者只匹配顶层，嵌套目录的 `.db` 不被忽略。涉及隐私数据时**放置路径本身就是安全措施**。改完必须用 `git check-ignore -v` 验证。

### 10.11 提交失败先怀疑 hook

> **判据**：`pre-commit run --all-files --verbose` 先跑一遍，**不用 `--no-verify`**。ruff/mypy 版本打架通常是因为 hook 用隔离环境（改 `repo: local` + `language: system`）。

### 10.12 网络失败：重试，不改 remote

> **判据**：间歇性不可达就重试或延后到下一轮。**绝不**强推 / 改 remote / 重写历史 / 删 reflog。

### 10.13 删除类操作五条

> **判据**：
> ① **每次都要确认**，不是只第一次；
> ② **先列清单再停**，输出格式统一（让人能一眼审完）；
> ③ 优先"**移出版本库**"而非"从磁盘删除"；
> ④ **未跟踪文件不要 `rm`** —— 移出即可（删了不可恢复）；
> ⑤ **禁止 `git clean -fd`** —— 会一次清掉所有未跟踪的过程性文件。

### 10.14 未推送的代码无法被 CI 验证

> **判据**：需要 CI 验证时，**先确保已推送**（必要时开分支）。本地跑通不等于 CI 跑通，未推送的分支在 CI 眼里不存在。

### 10.15 双仓库 / 跨环境部署的五条裂缝

| 风险 | 对策 |
|---|---|
| **绝对路径泄露用户名** | 配置只准 `~/` 开头；单测断言不含 `/home/`、`/Users/` |
| **CI 日志泄露路径**（日志默认公开） | CI 不用默认路径；输出脱敏 |
| **示例目录与真实目录混淆** | 单测断言两者不等；写入前校验目标不在代码仓库内 |
| **备份缺失** | `doctor` 检查 remote，无则 warning（不静默） |
| **版本控制与云同步打架** | 二者选一，不要同时 |

## 11. 产物、文档与版本

### 11.1 周期性产物文件名必须含周期标识

> **判据**：**固定名 = 覆盖 = 丢历史。** 而跨期对比（L3/L4 自验证）恰恰是最需要历史的能力。固定名只在"永远只看最新一次"的场景成立。

### 11.2 入库判据：两问

| 问 | 说明 |
|---|---|
| ① **有没有下游消费者？** | 有代码读取它吗？有就入库 |
| ② **本地能重新生成吗？** | 不能重新生成的（依赖特定环境/外部数据），丢了就没了 → **必须入库** |

> **第 ② 问比第 ① 问更根本**：能重新生成的丢了可以再造，不能的丢了就永远没了。
> ⚠️ **"人要看"也算消费者**。别因为"没有代码读它"就否定入库（此时改用限定范围的脏树检查来隔离影响）。

### 11.3 不入库 ≠ 看不见

> **判据**：决定"不入库"时，**必须同时给出给人看的通道**（CI summary、artifact、本地路径）。否则只是把信息藏起来。
> 同理：**沉淀文档自身也要有载体保障**——要么入仓，要么明确指定备份位置并验证可达。内容再好，载体丢了等于没写。

### 11.4 ★ 文档体系：三层 + 一类（每层只放"只有它能回答"的内容）

> **建文档时按三层 + 一类配齐。分层判据：删掉它，别的文档能不能回答它负责的那个问题？能 ⇒ 冗余，别加。**

**① 意图层 SSOT——决策者执笔或批准**

| 文档 | 回答什么 |
|---|---|
| **设计方案** | 「为什么这么做」——判据、边界、取舍。**与代码冲突时以「它 + 决策者裁决」为准**（不是默认代码错，也不是默认文档对） |
| **执行手册** | 「怎么做」——红线、坑位、环境分级、里程碑、收尾纪律 |
| **版本账** | 「文档有没有跟着代码走」——文档 ↔ tag ↔ 日期 ↔ 状态 |
| **花钱账本**（涉及外部 API 时） | 「钱花在哪、上限多少」——价格来源 + 估算 → **实测回填**（§8.19） |

**② 证据与账本层——执行方写**

| 文档 | 回答什么 |
|---|---|
| **数据源手册** | **真实**响应片段（可截断）、规模口径链。**不可达就写"未获得 + 原因"，禁止编造** |
| **时间账 / 开发日志** | 按时间记的事实、实测、踩坑——**事故回溯第一站** |
| **教训库 / 经验固化** | 可迁移教训，编号沉淀——**所有结论的最终回流地** |

**③ 门面层——对外**

| 文档 | 回答什么 |
|---|---|
| **README** | 能力 + 命令 + 路线 + 合规署名 |
| **CHANGELOG** | 按版本 / 里程碑记交付了什么 |
| **CONTRIBUTING** | 怎么参与 |
| **Agent 工作手册** | 用 AI 协作时：架构、红线、改哪里先跑什么 |

**④ 工作流文档——不属文档体系本体**

> 阶段交接（handoff）、任务卡（DoD + 范围）。
> **四条全中即为工作流**：有时效 / 可归档 / 结论外流 / 不面向长期读者。
> **别把它们算进"项目文档"**——它们是过程载体，结论回流到教训库即可。

> **归属可变，分层不变**：谁执笔可以变（决策者全权写 → 交给执行方写 + 决策者保留批准权），
> 但"**意图归决策、证据归执行**"的分层不能变。**分层站得住，换谁执笔都不会乱。**
>
> 配套：**规格与流水分离**（变更频率差一个量级，放一起会让高频改动淹没稳定规格）；
> **说文档集合时必须指名，不用"四份"这类数量代称**（数量会重合，名字不会）；
> **同一结论只保留一份**，其余删除或改成引用（两处会同时被修改 ⇒ 其中一处该是引用）；
> **实现者不改意图层**——变更追加到独立变更记录文件。

### 11.5 版本由 VCS 管理，不由文件名管理

**反模式**：文件名带版本号 → 堆积 N 个历史文件，"哪份最新"变成需要人判断的事；文件名带恒定但错误的版本（`设计 v1`，内容已 v1.20）→ 更隐蔽的误导。

> **判据**：① 文件名固定；② 版本写文档头；③ 另建维护日志 `| 文档版本 | 对应 tag/commit | 日期 | 一句话总结 |`；④ **先提交代码打 tag，再刷新文档**——**写不出 tag 列就说明顺序错了**，这条把纪律变成了可执行的形式。

### 11.6 「待并入文件」模式

> **判据**：未到提交时机的文档改动，放进**明确的"待并入"暂存文件**并记在交接清单里，到时机再并入。**不要靠记忆。**

### 11.7 版本号改动是「多点同步」清单

> **判据**：版本号不只出现在一处（文档头 ×N + 交叉引用 + 维护日志 + 简报）。改动时**列出所有出现位置**逐一同步，改完全文搜索验证残留。历史引用（如"v1.21 摘要标题"）**正确保留**，不要一并改掉。

### 11.8 小版本膨胀：阶段内分步，不加子版本

> **判据**：阶段内的小改动**累加进下一个正式版本**，不单独发子版本；子版本只用于已发布版本的紧急修复。阶段内分步（如 S2a 数据侧 / S2b 生成）对外仍是一个阶段，同时保留归因能力。

### 11.9 插入章节前先列出该层级的全部编号

**实例**：凭印象写 `§11.2`，实际已被占用 → 差点覆盖既有章节。

> **判据**：插入前先 grep 出该层级的**全部编号**，确认空位再写。**动排序类结构前先看清既有规律**（升序还是降序），不要凭"应该如此"去"修正"。

### 11.10 ★ 表格是编辑错误残留重灾区

**实例**：一次收尾通读发现 4 处问题，其中 3 处是**既有缺陷**（里程碑表有重复行、章节缺号、状态过时）——grep 锚点式检查抓不到。

> **判据**：交付前做一次**逐节通读**（不是 grep 锚点），**表格逐行看**。通读发现的既有缺陷要单独列出，区分"我引入的"与"本来就有的"。

### 11.11 折叠区 = 看不见

> **判据**：重要信息不要放进折叠块/附录。**"读者理解结论可信度的前提"必须在正文最前面。** 折叠区适合放：详细口径、次要证据、完整推演过程。

### 11.12 配置项不能"文档说有、代码没有"

> **判据**：删除一个配置项前，先让所有文档停止引用它，顺序不能反。暂时无法同步就**保留兼容别名并打废弃日志，不要直接删**。

### 11.13 用机器门禁兜底人为遗漏

> **判据**：凡是"容易忘且错了代价大"的约定，写成**自动化断言**（如文档一致性测试校验指针/归档/版本号），而不是写进文档让人记。文档同步是纪律不是建议，但纪律要靠门禁兜底。

### 11.14 ★ 描述与产出必须一致

**现象**："我已升级到 v1.20" —— 但文件实际是 v1.19。

> **为什么严重**：它比功能 bug 更伤，因为**破坏的是协作的基础信任**——接收方无法判断该信你的话还是该信文件。

> **判据**：
> - 不确认的事**不升版本号**；不确定的内容**不写进文档**
> - **凡说"已更新"，必须当场给出文件**
> - **凡说"你留着"，必须当场交付**（"你本地保存"这种中间态等于没做）
> - 文档刷新是**显式步骤**，不是"顺手做"——声称刷新却没刷，是本项目反复出现的事故类型

### 11.15 新建文档前的「准生证三问」

> **判据**：新建一份文档前先答——
> ① **它回答什么问题？**（答不出 ⇒ 冗余，别建）
> ② **谁能改？**（意图层归决策者 / 证据层归执行方；归属不清会导致互相覆盖）
> ③ **什么时候作废？**（**答不出的多半是过程文档** ⇒ 不入库，结论回流到教训库即可）
>
> 这比"文档规范"更能挡住文档膨胀——**大部分该砍的文档都死在第 ③ 问。**

### 11.16 文档体系的三条规模纪律与三条反面清单

**规模纪律**：

| 条 | 内容 |
|---|---|
| 1 | **SSOT 变长是正常的**（参考量级：1500 行），但要配**"读指定章节"的导航约定**——靠全量阅读维持的 SSOT 必然失效（§0.1） |
| 2 | **工作流文档必须短**（参考量级：< 160 行）。**长了说明它在偷当 SSOT 用**——把结论外流到教训库，把规矩上移到意图层 |
| 3 | **能生成就别手写**：数据源手册由脚本实跑生成 ⇒ 永远不漂移。**凡能这样干的文档都这么干** |

**双账本**：**时间账**（记事实，可废）+ **版本账**（记版本，可审计）。
缺一个就回答不了"这个文档是不是过期的"。

**反面清单**：
- ❌ 别把工单 / 交接当文档体系（越攒越多，且永远不清）
- ❌ 别让对外门面承载内部约定（README 里写内部红线 = 既对外失焦又对内无约束力）
- ❌ **别在入库文档里引用不入库的文件**（= **幽灵引用**，读者打不开，且你不知道它已经失效）

## 12. 人机协作（AI 辅助开发）

### 12.1 三方分工

| 角色 | 负责 | 不负责 |
|---|---|---|
| **人（你）** | 目标、优先级、验收、越权事项决策 | 具体实现 |
| **AI 助手（对话侧）** | 判断、方案设计、验收评审、独立复核 | 读仓库（通常无权限） |
| **执行 Agent（有仓库权限）** | 实现、实测、用仓库事实证伪方案 | 改规范层文档、定优先级 |

### 12.2 ★ 让拥有事实的一方拥有否决权

**做法**：给出方案时明确附上"你有 XX 而我不能访问，凡与实际情况不符或有更好方案，**直接反对并说明理由**，不要迁就。"

**实证**：执行 Agent 三次用实际数据反对了对话侧的方案——反对"取最长段"（破坏跨期可比性）、反对用已被占用的词作第三态、反对直接删配置项（规范文档还在引用它）。

> **判据**：否则方案会以"正确"的面貌落地，而错误无人发现。**它离代码近，我离代码远**——在"具体怎么做"上，它的信息优势是压倒性的。

### 12.3 ★ 声称产出 ≠ 产出（被违反 10 次以上的高频错误）

**现象**：在回复里写出了完整内容，或口头说"已新增 X""已修复 Y"，但**文件没落盘 / 没重新打包 / 没真正写入**。

**两个根因**：

| 机制 | 说明 |
|---|---|
| **生成文字 ≠ 落盘** | 写出内容消耗了真实思考，被编码为"工作已完成"，但写进回复和写进文件是两个独立动作 |
| **代理指标代替真验证** | 查了"文件存在""行数相同"，但没验证"我说的那句话真的在里面" |

**四条杜绝措施（不依赖自律）**：

| # | 措施 |
|---|---|
| 1 | **声称产出时必须贴验证输出**，且验证**针对那个具体断言**（不查"文件存在"，查"我说的那句话在文件里"） |
| 2 | **打包后验证包内文件**，不是验证源文件（逐字节比对，不比对行数） |
| 3 | **一次只声称一个产出**，多个产出分条独立验证 |
| 4 | **撤回过的结论进禁区**，同一对象二次涉及时强制重读原文 |

> ⚠️ **诚实说明**：立纪律本身治不了这条——立过之后仍连犯两次。真正起作用的是**外部抽查**：把证据摆出来，让人随时能查。最容易出事的时刻：**一次性声称多个产出**。

### 12.4 文件路径 ≠ 交付

> **判据**：隔离环境（沙盒/容器内）生成的文件，对方根本访问不到。要么**把内容内联进指令/回复**，要么通过对方可达的通道（下载链接、附件）送出。这条被踩过多次。

### 12.5 ★ 四类事必须停下来问（越权事项）

| 类别 | 示例 |
|---|---|
| **数据在哪里** | 权威数据源是哪个、本地副本是否过期 |
| **本地能不能跑** | 环境依赖、网络可达性、密钥（无外网 ≠ 所有功能都跑不了，导出/渲染可能不需要网络） |
| **字段复用 / 新增** | 先问"是否已有字段能承担"（不可逆，影响迁移） |
| **优先级排序** | 用户点名的需求自动 P0，你的规划排其后 |

> **判据**：命中任一类，Agent 不得自行决策。**提问必须带方案原文**——只抛问题不带上下文，等于把决策成本推给用户。
> 配套**双通道**：**事实性问题**（数据在哪、代码有没有、跑没跑过）交给有环境访问权的一方；**意图性问题**（要不要做、优先级）留在决策方。混着问会得到"执行方替你决定意图"。

### 12.6 ★ 会话切换最大的成本不是恢复知识，而是恢复"该问什么"

**事故**：负责人重开会话做后续开发，判断"状态已外置到 SSOT/简报/经验文档，重开无损失" → 新会话按错误前提做完了整个方案，**且它自己完全不知道该回来问**。致命矛盾藏在推理步骤里，不在结论里，被盲审时拦下。

| 失败模式 | 表现 | 是否会被发现 |
|---|---|---|
| 知识缺失 | "我不知道，需要查" | ✅ 会暴露 |
| **不知道该问什么** | **"我很确定，方案完整"** | ❌ **安静地错到底** |

> **判据**：
> ① 重开会话时，**"必须提问的场景清单"比"项目知识"更重要**——知识错了会暴露为"我不知道"，"不知道该问"会表现为"我很确定"；
> ② **★ 外置的是事实，不是判断**——文档能存结论，存不了"什么时候该停下来问"；
> ③ **★ 状态外置做得越完整，越危险**——它会让你以为"够了"，从而停止去找那些没写下来的东西；
> ④ **复核必须看原文**：摘要会藏住推理错误，只审结论等于没审；
> ⑤ **给建议时自查：谁承担了大部分成本？** 如果是对方，我有没有低估它（自利偏差）。

### 12.7 交接文档必须自包含

> **判据**：**不要把自己的连续性押在会话上下文上。** 标准是"能直接照着干活"，不是摘要。写完问一句："一个完全没有历史上下文的人，读完能立刻开工吗？"
> 重开前的顺序：**先写文档 → push → 确认 CI 绿 → 重开**。重开的代价不是丢失对话，是丢失**没写进项目文档的东西**。

### 12.8 协作启动 SOP：第一轮逐条核对基线

> **判据**：新会话/新阶段的第一轮，用**封闭问法逐条核对**，不要用"你有什么要问的吗"这类开放问法——开放问法会漏掉你没想到要问的东西。核对项至少：当前阶段、最新 commit、文档版本、已知遗留、本轮目标。

### 12.9 双会话模式（推荐用于长项目）

| 会话 | 职责 |
|---|---|
| **主会话** | 全局统筹、关键节点决策、审阅验收报告。**不写代码** |
| **辅会话** | 讨论实现细节、跟随开发过程。**寿命 = 一个子阶段，做完即弃** |

> 四条补充：① **主会话也要定期换**（只决策也会衰减，靠启动包恢复）；② **辅会话不可跨阶段累积**（那正是长会话失效的方式）；③ **加"第三方校验"动作**——在新会话里只做一件事：核对文档与代码是否一致；④ **大阶段间强制上下文重置**，以"下一阶段 handoff 作为唯一上下文入口"，不让旧结论默认延续。

### 12.10 必须 `/clear` 的信号

| 信号 | 说明 |
|---|---|
| **失败-修复循环超过 3 次** | 最强信号 |
| 切换任务主题 | 如从"写测试"改成"修 bug" |
| AI 开始复述错你的需求 / 重复问同一问题 | 上下文已混乱 |
| 早已定下的事又问一遍、引用你没给过的文件、建议与前面裁定矛盾 | 已失控（任一即需重建） |
| 项目结构大改、明显感觉它变慢 | 上下文膨胀 |

> **不必 clear**：单会话 < 10 轮、一次性产出、中间无失败重试、承接上一轮的只读结果。
> 重建成本很低：贴一份 300 字摘要（到哪一轮 + 关键决策 + 卡在哪）即可接上。

### 12.11 退化信号与被质疑时怎么答

> **判据**：出现以下信号即视为退化，应主动提示对方考虑重开会话——开始把推断写成事实 / 一次性声称多个产出 / 重复犯刚被指正过的错误 / 输出结构开始松散。
> **被质疑质量时**：① **承认**并给出可验证的失误清单；② **归因到机制**而不是态度；③ 给出**不依赖自律的纠正措施**。空口保证"我会注意"没有价值。

### 12.12 协作七条纪律

1. 先核实再开口
2. 区分"已核实"与"推断"，并在表述中标注
3. 主动请求证伪自己的方案
4. 越权事项（§12.5）必须停下来问
5. 结论必须带证据
6. 承认自己没有的权限（读不到仓库就直说，不猜）
7. 决策留痕（写进清单/文档，不靠记忆）

### 12.13 ★ 一次只做一件事

**失控信号**：每个阶段结束都有"顺带修"的尾巴 · 文档永远比代码慢半拍 · 收到的待确认项超过一个。

> **判据**：
> - **待确认项 ≤ 1**（超过即说明在并行推进）
> - 明确写"本次不做其他任务"
> - **AI 不会自己停下来**——必须在指令里显式写"完成后停下"
> - 并行不只是任务并行，也包括**会话并行**（多个会话同时推进同一项目）

### 12.14 分级授权

> **判据**：push / 不可逆动作**逐次授权**，不批量默认执行；**花钱先列预算**；每阶段独立交接文档。高风险动作显式确认，不靠"之前同意过"。

### 12.15 输出协议：结尾固定两块

> **判据**：每次回复结尾固定给「**下一步要人做什么**（可直接执行）+ **这些事需不需要人先确认**」。长对话里最易发生的失效不是"答错"，是"答对了但对方不知道下一步干嘛"。涉及写操作/不可逆动作时显式标注，并把**为什么安全**一起说。
> 配套：**跨会话 / 跨 AI 传递内容一律原文块**，不给口述步骤（口述会在转达时被补全，而补上的往往是错的）。

### 12.16 状态摘要按需提供，不主动塞

> **判据**：约定"需要时主动索取"，不"定期投喂"——定期贴会稀释注意力。AI 在关键节点（切模型、clear、方向判断）主动索取；摘要本身也落盘，不临场整理。

### 12.17 四条容易忘的收口动作

> **判据**：
> ① **用户误解 = 文档缺口**——遇到误解不要只澄清一次，当场转成一条文档待办（能被误解 = 文档里就没写）；
> ② **用户明确认可的行为当场归档**——口头认可不写下来，和没发生过一样，下次新会话不会继承；
> ③ **已知概念要迁移到新场景**——老场景早已解决的问题在新场景重复出现，往往是因为概念没有显式迁移；
> ④ **区分「增补」与「重排」**——鼓励提改进，但推翻既有结构代价高，需显式确认，不能混在"优化建议"里一起执行。

### 12.18 生产数据与质量底线

> **判据**：① 涉及只读生产数据时，**先记录校验值**（sha256），每次改动后验证未变——最便宜也最可靠的安全网；② **不确定就问，不要猜着做**，返工成本远高于等待成本；③ **不要为了让测试通过放宽阈值**。

## 13. 阶段推进 SOP（重构 / 长任务 / 多会话）

> **核心矛盾**：AI 只看得到当前会话，而你的计划横跨十几个会话。所有规则都是围绕这一条展开的。

### 13.1 阶段划分：按"依赖闭合"切，不按"工作量"切

> **判据**：**一个阶段 = 一组依赖已就绪、可独立验收的改动。** 错误切法（按工作量）会导致一半测试依赖的模块还没实现。

### 13.2 每阶段固定四步

```
核对 → 实现 → 验收（含实跑）→ 提交 + push
```

**核对在前，实现在后**——这是最重要的一条。

### 13.3 开工前两项必做核对

**① 依赖闭合检查**：这个阶段要写的东西，依赖的模块是**真实现还是存根**？只要有一个是存根，就先补实现。否则 AI 会瞎猜实现方式，产出"看起来完整、实际错误"的代码——它不会报错，只会安静地给出错结果。

> 操作：给指令前先列一张状态表（模块 / 依赖 / 状态），成本一张表，收益是挡住绝大多数"指令看着完整但依赖没闭合"的坑。

**② 命名核对**：**凡是已有代码/存根定义了的名字，一律沿用；指令只描述行为，不指定名字。** 真实案例：指令写 `compute_perplexity`，存根实际是 `loss_to_perplexity` 且已被导出。

> 操作：每个新阶段开工前一次只读核对（打印存根签名 + `__init__.py` 导出 + docstring 预期行为），**不要假设自己记得住名字**。

### 13.4 阶段之间的动作

```
/clear → /init → grep 验证约束 → 粘贴指令
```

| 动作 | 为什么 |
|---|---|
| `/clear` | 清掉失败重试的上下文膨胀；防止废弃方案被捡回 |
| `/init` | 重新扫描项目（代码已变，知识图谱不同） |
| `grep` 验证 | **`/init` 会重写约束文件**，必须确认约束还在 |
| 粘贴指令 | 指令从规划文档复制，不临场发挥 |

**硬约束必须沉淀进约束文件**（`CODEBUDDY.md` / `AGENTS.md` / `CLAUDE.md`）——它是跨会话的记忆载体，`/clear` 清不掉。**放在文件靠前位置**（重写时末尾最容易被截掉）。真实后果：约束丢失后，AI 手贱给某个变量赋值，把已修好的 bug 原地复活。

### 13.5 验收要"实跑"，不能"只改代码"

> **判据**：每个阶段的验收必须包含实际执行并贴出输出。只改代码不验证，问题会累积到最后阶段集中爆发。**第一次端到端跑通是项目的关键节点，越早越好。**

### 13.6 AI 建议的过滤与采纳

| 过滤（不采用） | 为什么 |
|---|---|
| **推荐指令** | 它不掌握跨会话计划 |
| **commit 编号** | 局部视角，会与全局规划撞车（编号归属权在你） |
| **改 pyproject / CI / 公共契约** | 影响面大，先问再做 |
| **"顺便改一下 X"** | 会让两阶段的改动混进一个 commit |

| 采纳（它的偏离常是对的） | 实例 |
|---|---|
| 用实测否掉我的假设 | "确认 bf16 是否跳过 GradScaler" → 它发现 bf16 路径**根本不存在** |
| 发现更隐蔽的边界 | "不得给 A 赋值" → 它发现替换 B **也会隐式打断 tie** |
| 用实测纠正我的可行性判断 | 我写"medium 可跑" → 它实测 9.05 GiB 超 8 GB 显存 |
| 阈值冲突时列方案让你选 | 而不是偷偷放宽 |

> **判断标准**：`依赖闭合 + 不越界 → 让它跑完，事后补核对`；`越界 或 依赖未就绪 → 立即制止`。
> **误执行后的处置**：不要中断让它回退（可能留下半成品，比跑完更糟），跑完再补核对，提交时按路径拆分即可。

### 13.7 值得鼓励的 AI 行为（可主动引导）

- 主动做幂等性验证（md5 指纹前后比对）
- 用 CI 干净环境佐证本机问题不是仓库问题
- 发现原则性问题主动推广到同类文件
- 遇到阈值冲突不偷偷放宽，而是列方案让你选

### 13.8 常见失败模式速查

| 现象 | 根因 | 对策 |
|---|---|---|
| AI 产出"看起来完整但错误"的代码 | 依赖未闭合，它瞎猜实现 | §13.3① |
| 函数名对不上 | 用习惯起名而非仓库契约 | §13.3② |
| 约束失效导致 bug 复活 | `/init` 重写了约束文件 | §13.4 每轮 grep 验证 |
| 文档说"改动丢了" | **是文档滞后，不是代码丢失** | 看"原内容 vs 现状"两列，别慌 |
| 提交反复失败 | **先怀疑 hook，再怀疑代码** | §10.11，不用 `--no-verify` |
| ruff/mypy 版本打架 | hook 用隔离环境 | 改 `repo: local` + `language: system` |
| 大文件差点入库 | gitignore 单行多模式不生效 | §10.10 |
| `git log` 显示不全 | 输出被终端截断 | §10.8 |
| 测试"通过"但什么都没跑 | mark 过滤导致静默选 0 个 | §7.9 |
| 阈值不可达产生假失败 | 预设阈值未实测 | §7.10 |

### 13.9 验收清单模板

```
- [ ] 依赖闭合已核对
- [ ] 命名已核对（沿用存根契约）
- [ ] make lint 通过
- [ ] make test 通过（用例数应增加或持平）
- [ ] 既有测试未受影响
- [ ] 端到端实跑通过（贴出输出）
- [ ] 提交已拆分（一个 commit 一类改动）
- [ ] 已 push
```

### 13.10 需求锚点：防止方向跑偏

**误判实例**（写进约束文件顶部）：

```
审计样本不足（真的） → 工具能力见顶（半真） → 整个项目该收尾（假的）
```

错在最后一环：把**局部模块的边界**当成了**整体项目的边界**。

> **判据**：把原始需求固化到约束文件顶部，标注**"不可由后续讨论覆盖"**。提任何方向性方案前先自答三问（可判定，不是开放式）：
> 1. 这推进「核心目标 1」吗？
> 2. 这推进「核心目标 2」吗？
> 3. 跑完能否端到端完成一个真实案例？
>
> 任一为否，不得以此为由收尾或转向。**特别注意：用"技术够不够"回答"要不要做"，是最常见的错误。**

### 13.11 决策自己拍，不让实现方替你决定方向

> **判据**：实现方不知道你的全局约束（时间成本、主线优先级、还剩几个项目）。它优化的是"技术上更完备"，你要的可能是"够用就好"。**实现方不会主动叫停（它有实现惯性）**——你问它"不做的理由是什么"，它会说。

## 14. 提示词模板库

> 全部来自真实项目验证有效的提示词。模板可直接复制，方括号内替换。**理由部分不要删**——它决定执行方遇到模板未覆盖的边界时怎么取舍。

### 14.1 新会话重建上下文（用得最多、最关键）

```
这是 [项目名] 项目。先读下列文件重建上下文：
1. [docs/process.md]      —— 进度、决策台账、待决项
2. [CODEBUDDY.md]         —— 硬约束
3. git log --oneline -20  —— 最近提交

当前状态：
- [已完成：...]
- [进行中：...]
- [未提交改动：...（先确认是否要提交）]
- [待修问题：...]

本次任务：[具体任务]

⚠️ 先做一件事：检查是否有未提交改动，有就按类型拆 commit 提交。
做完停下报告，不要自动开始下一阶段。
```

> **为什么有效**：先读文件 = 拿到完整规格而非二手转述；显式列未提交改动 = 避免新旧会话打架；末尾停下条件 = 防止跑过头。
> **失败对照**：只说"继续"——新模型不知道上下文，必然瞎猜。

### 14.2 中断后要求自检并汇报

```
先不要继续写代码，先做三件事：

1. 报告当前的真实状态（以磁盘为准，不要凭记忆）：
   - git status / git log --oneline -10
   - 有哪些文件、最后修改时间
   - 测试是否跑得通

2. 判断中断时做到哪一步：
   - 有哪些已完成
   - 有没有半截的实现
   - 有没有挂着的待决问题（区分「中断的任务」和「待决问题」）

3. 报告后停下，等我确认下一步。
   不要自动开始补完，也不要自动重做。
```

> **为什么有效**：「以磁盘为准」——它的记忆可能和磁盘不一致，而磁盘是事实；「区分中断的任务和待决问题」——两者处理方式完全不同。

### 14.3 带硬约束的实现指令（主力模板）

```
[模块名]：[一句话目标]

⚠️ N 条硬约束（违反任何一条就算失败）：
1. 严格按 [文档名] 第 [X] 节实现，不得简化、不得合并条目
2. [最容易偷工减料的地方] 必须全部实现 —— 这是最容易被跳过的地方
3. [豁免/边界条款] 必须实现
4. 每条产出必须带 [证据类型，如 file:line]，带不出就降级
5. 每完成一组就跑 [测试/lint/类型检查]，全绿才继续
6. 不要修改 [参考目录 / 已通过的测试 / 核心模块]
7. 不要为了让测试通过放宽阈值

做完停下报告，输出 [验收产物]。不要自动进入下一阶段。
```

> **第 2 条是关键**——主动点名最容易偷工减料的地方。不点名的话实现方会默认简化，而这类简化往往能通过测试但语义错。

### 14.4 设计先行，不写代码

```
先给我设计，不要写代码。

设计必须包含：
  1. 定位（一句话：这个东西做什么、不做什么）
  2. 输入（有哪几样，缺了怎么办）
  3. 输出（落到哪里，什么形态）
  4. 检查点（每一步怎么判通过 / 不通过）
  5. 明确不做（列出至少 3 条）
  6. 验收清单（可判定的条目，不要"确保质量"这种空话）

约束：[约束 1] / [约束 2]

设计给出来后停下，等我确认再实现。
```

> **为什么有效**：设计错了改设计便宜，代码错了改代码贵；「明确不做」列 3 条以上防止边界含糊；验收清单要可判定。
> 实证：这一步拦下过"差点混入规划算法""差点发明多余环节""漏了前置条件"三处问题——在纸面上发现比在代码里发现便宜一个量级。

### 14.5 方案评审后放行（带补充约束）

```
设计通过，[哪几条] 都认可。开始实现。

实现时补上这几条（第一处必须修）：
  [必须修的问题 1 —— 说清现象 + 根因 + 改法]
  [补充 2]

验收清单逐条自查，每条给出对应的测试用例名。
做完停下报告，不要自动进入下一步。
```

> **为什么有效**：明确"哪几条认可"避免它以为全通过；"第一处必须修"把最重要问题排最前；"每条给出测试用例名"防止说"已验证"但没测。

### 14.6 分步推进 + 每步停下

```
按 [顺序] 逐步做。每步做完停下报告，不要自动进下一步。

每步报告要包含：
1. 实际输出（贴关键片段，不要只描述）
2. 有没有"判了但看不懂"的地方
3. 你自己觉得卡在哪（如果有）

第 2、3 条比"跑通了"更重要 ——
跑通只说明机制可行，卡住/看不懂才说明要改什么。
你的主观感受是有价值的信号。
```

> **第 3 条尤其重要**：实现方的"卡顿感"常常是设计缺陷的早期信号，但它不会主动说，除非你问。

### 14.7 纠偏：指出层面错位并要求修正根因

```
这个判断不成立。根因不在 [它认为的地方]，在 [真正的地方]。

实测：[给出证据，命令 + 输出]

你的方案是「[它的方案]」，这解决的是 [表层现象]，
但真正的问题是 [根因]。

改为：[正确的做法]
理由：[为什么]
```

> **为什么有效**：先给实测证据（不给证据的纠偏容易被当成主观意见）；明确指出"你解决的是 X，真正的问题是 Y"让它看到层面错位；直接给替代方案，不让它自己再想一遍（可能又想歪）。

### 14.8 规则修正（必须给根因，不只给现象）

```
[规则名] 判定错了。

现象：[具体表现]
反例：[触发误报的真实案例]
根因：[你分析的根因]

修正为：[具体判据/算法]
判据：[一句话说明边界在哪]

回归测试：
  - [反例] → 不报
  - [真缺] → 报，且证据含 [关键信息]
```

> **只给现象，实现方会打补丁（收紧阈值）；给根因，它才会改设计。**（对比见 §7.5）

### 14.9 要求配"故意失败"的用例

```
每个检查点必须配一个"故意让它失败"的用例。
只测通过测不出失效。

对每个检查点，问自己：
  如果这个检查点的判据写错了，现有测试会发现吗？
  不会 → 补反向用例。
```

### 14.10 要求报告真实数字，不许为了好看

```
报告两个数，逐条列，不回避：

1. [度量项 A]（逐条列出，不要只给总数）
2. [度量项 B]（逐条对账）

⚠️ 真实数字优先。
若某处需要人工介入，如实计入，不要为了让数字好看而回避。
若跑不通，如实报告卡在哪，不许放宽判据或造假。
```

> **为什么有效**：明确说"不许为了好看"，它才会报真实数字。不说的话，实现方倾向于把不方便的数字藏进角落或降级处理。

### 14.11 双目标验证（正例 + 反例）

```
用两个目标一起验证：
  正例目标 → [召回率]（该报的是否报了）
  反例目标 → [误报率]（健康对象上应该报 0 条）

反例目标报出的每一条都逐条看：
  - 报出真问题 → 有效（意外收获）
  - 报出误报 → 正是要找的
  - 报 0 条 → 只证明"不吵"，必要但不充分
```

### 14.12 让实现方自审（暴露它自己没发现的问题）

```
现在做一件事：自己审自己，找出你还不知道的问题。

1. 列出 [本次产出] 里所有"判了但其实判不了"的地方
2. 列出所有"降级/跳过/豁免"，说明每一处是否可见
   （只进日志不算可见，必须出现在交付物里）
3. 列出所有"若 XX 则 YY"的隐含假设，指出哪些不成立时会静默出错
4. 如果你觉得某处设计有问题但没改，说明为什么

不要粉饰，不要只报好消息。
```

> **关键**：第 2 条（降级是否可见）是这类系统最隐蔽的失效点——降级静默发生，用户以为在生效。

### 14.13 止损线（切低成本模型时用）

```
⚠️ N 条止损线（触发任一立即换回强模型）：
1. 同一处错误修 2 次修不好
2. 需要反复纠正"按文档来"超过 2 次
3. 验收数字明显不对
4. 擅自简化 [抑制边/豁免条款/边界条件]
   —— 这条最危险，能通过测试但语义错
```

### 14.14 收尾四项

```
1. 提交所有改动（按类型拆 commit）
2. 把 [本次的关键证据] 记入 [docs/process.md]
3. 更新 README，必须包含：
   - 一句话定位
   - [已验证的案例/数据]
   - 明确列出不覆盖什么
   - 用法
4. 更新状态摘要

写完报告改了哪些地方，不要 push。
```

> 第 3 条里的"明确列出不覆盖什么"是关键——它把文档从宣传材料变成可信材料。

### 14.15 让对方判断「要不要做」

```
不要直接开始做。先回答：
1. 这个方向做下去，最大的不确定性是什么？
2. 做到什么程度算"验证过了"？给出一个可判定的标准
3. 你觉得不做的理由是什么（如果你有）
4. 如果做，最小的验证成本是多少

回答完等我决策，不要开工。
```

### 14.16 模板的共同结构：五段缺一不可

| 段 | 作用 | 缺失后果 |
|---|---|---|
| **上下文** | 读哪些文件、当前状态 | 它凭记忆猜 |
| **目标** | 这一次要什么 | 做偏 |
| **约束** | 硬约束、明确不做 | 偷工减料 / 范围膨胀 |
| **验收** | 可判定的清单 | 说"已完成"但没测 |
| **停在哪** | 做完停下，不自动继续 | 跑过头，返工成本翻倍 |

> **最容易被省略、也最不能省的两段：`明确不做` 和 `停在哪`。**

### 14.17 四条元原则（所有模板背后的一致性）

1. **给根因，不只给现象** —— 给现象会收获补丁，给根因才会收获修正
2. **明确说"不许做什么"** —— 不说的默认行为一定是取巧（放宽判据、藏数字、简化边界条件）
3. **要原文，不要转述** —— 转述会丢掉你本该看见的东西
4. **每轮末尾固定两项** —— 需要对方做什么 + 是否需要确认

## 15. 收尾检查清单

> 任何项目阶段性结束时过一遍。

### 15.1 一致性

- [ ] 文档版本与代码 tag 有明确对应（维护日志）
- [ ] 没有"描述了但没交付"的文件
- [ ] 没有"版本号升了但正文没跟"的文档
- [ ] 重命名后所有引用已同步（grep 旧名应为 0）
- [ ] 没有两份文件描述同一件事
- [ ] 没有"文档说有、代码没有"的配置项

### 15.2 可观测性

- [ ] 每个降级分支都有记录且**进产物**
- [ ] 关键指标可 diff（产物版本化 + 结构稳定）
- [ ] 有"空态"和"失效"的区分手段
- [ ] 每个外部依赖有**独立**健康监控
- [ ] 确认过**每个功能都真的产出过非空内容**

### 15.3 验证充分性

- [ ] 所有自动化**实跑过一次**（不只是测试通过）
- [ ] CI 绿（本地过 ≠ CI 过）
- [ ] 每个检查点配了"故意失败"用例
- [ ] 时间相关逻辑有跨周期测试
- [ ] 生成类功能有自动评估，且含 L2 信息增量层
- [ ] 涉及输出质量的功能**真跑过一次**（不只跑桩）

### 15.4 可恢复性

- [ ] 新接手者（或新会话）能快速知道"做到哪了、还剩什么"
- [ ] 这个信息不依赖任何人的记忆
- [ ] 环境差异（本地 vs 线上）有明确说明
- [ ] 唯一副本（不可再生数据）已识别并有备份

### 15.5 诚实度与成本

- [ ] 未满足的需求**明确列出**，不粉饰
- [ ] 已知局限写在显眼处（如"样本量不足"）
- [ ] "没做到"和"做到了"分开陈述
- [ ] 显式声明"不覆盖什么"
- [ ] 计费功能有**实测成本**记录

### 15.6 经验固化

- [ ] 本次踩的坑已转成可执行的判据（不是"下次注意"）
- [ ] 同类问题第二次出现时已写进工程规矩
- [ ] 经验文档在版本控制内或备份可达

## 16. 一页速查卡

```
【核实】无知不是证据（否定断言先 grep）· "已完成"=待验证声称（代码/迁移/数据三层）
        · 基线每轮校验 · 转述数字保留区间与分母 · 外部事实标来源
        · 诊断先拿证据（长度+前500字分辨截断/格式/逻辑）· 诊断环境要真实
        · 改了规模必须回归（token/超时/配额）
【推断】推论每跨一步问实测支撑 · 空白不是证据 · 方向对≠机制对 · 论证越完整越找反例
【建模】时间三态（滞后用首次观测）· 两个时钟不混用 · 身份指纹排除观测值
        · 可再生 vs 不可再生 · 归因是数据属性（传播到所有计算）
        · 意图层≠入口层≠评估层 · 主键先数覆盖率 · 连续量不分层级档
【静默失败】状态进产物 · 加跳过前问"条件会不会长期为真" · 新功能回头查自动化
        · 退出码分级要显式转换 · 有没有功能没人确认过它产出过非空内容
        · 每个外部依赖单独监控 · 干净状态是有效信号
【测试】断言会恒真吗 · 配反向断言 · 每检查点配故意失败用例 · 反向测试>正向测试
        · 时间逻辑跨周期 · 不伪造 fixture · 阈值实测后定 · 证伪条件互斥且穷尽
        · 核心机制先小规模验证 · 自举验证（让工具审自己）· 可证伪性由代码判定
【LLM】代码算、模型判 · 绝不回显输入 · 检测+预防同步 · 不留模糊退路
        · 降级阶梯以纯文本结尾 · 双层呈现（专业层+阅读层）· 不合成单一分
        · 判断锚定可核查事实 · 严禁编造（数字引用/文字改写/图表重画）
        · 省钱：持久化 > 缩范围 > 条件跳过 > 降档（末位）
【架构】可测试性一票否决 · 单一职责+唯一出口 · 横切能力收敛 · 编排层是唯一事务边界
        · 单向流 · 幂等可断言 · 文件内不留运行时间 · 为下一个消费者设计产物
        · batch 优先 · 可达性≠可用性 · 单源失败不影响整体 · N+1 先算年量级
【自动化】本地过≠CI过（实跑）· 未推送的代码无法被CI验证 · pull 用 --ff-only
        · 追加步骤前通读脚本 · 两套配置面同步 · 并发写远端加锁
        · 一个 commit 一类改动 · 删除类操作五条（禁 git clean -fd）
        · 双仓库五条裂缝（路径泄露/CI日志/示例目录/备份/云同步）
【文档】三层+一类（意图层/证据层/门面层/工作流文档）· 分层判据：删了别人能答吗
        · 准生证三问（答什么/谁能改/何时作废，第③问答不出=过程文档不入库）
        · SSOT长正常但配导航 · 工作流文档须短（长了=偷当SSOT）· 能生成就别手写
        · 双账本（时间账+版本账）· 禁幽灵引用 · 门面不承载内部约定
        · 周期文件名含周期标识 · 入库两问（消费者/能否再生）· 单一真相来源
        · 先 tag 后文档 · 版本号多点同步 · 插章节前先列编号 · 表格逐行看
        · 描述与产出一致（说"已更新"当场给文件）· 机器门禁兜底
【协作】让有事实的一方有否决权 · 声称产出必须贴验证 · 路径≠交付
        · 四类事必须问（数据在哪/能否跑/字段/优先级）· 交接文档自包含
        · 重开会话最贵的是丢失"该问什么" · 结尾给操作指示+是否需确认
        · 一次只做一件事（待确认项≤1）· 分级授权（不可逆动作逐次确认）
【推进】阶段按依赖闭合切 · 核对→实现→实跑验收→提交push · 依赖闭合+命名核对
        · 硬约束进约束文件（每轮 grep 验证）· 明确不做清单 · 需求锚点三问
【收尾】自动化实跑 · CI 绿 · 未满足项列出 · 不覆盖什么显式声明 · 经验已固化
```

> **警示**：混在一起的结果是——通用的被具体细节淹没，专用的被当成普适真理误用。

### 17.1 从专用经验中已提炼出的通用部分

- **gitignore 规则要看匹配范围**：`data/*.db` ≠ `*.db`（前者只匹配顶层）。涉及隐私数据时**放置路径本身就是安全措施** → §10.10
- **稳定 > 精细**：不稳定的细粒度聚合 = 每天一个文件 = 累积落空 → §4.9
- **分母要对齐**：4% 与 76.7% 都对，因为分母不同 → §2.7
- **表格逐行看 / 插入章节前先列编号 / 动排序结构前先看规律** → §11.9 / §11.10
- **收敛性论述不能想当然**：只对"连续在榜"的条目成立，真实收敛条件是"当日预算 ≥ 当日新增所需花费"，预算过小表现为**持续性缺口**而非"慢两天就好" → §8.18
- **用实测取代估算**：不猜价格，报出单次调用实测成本再反推 → §8.19

## 18. 最后

> **好的工程不是"没踩过坑"，而是踩过的坑都变成了下次能自动挡住的规则。**
>
> 所以每次事故之后，问的不是"怎么修好它"，而是"**怎么让它下次不可能悄悄发生**"。
>
> 通用原则决定**你能走多稳**，项目专用经验决定**那个项目下次能多快接手**。
> 两者都要留，但**不要混在一份里**。
