## 1. ★ 真冲突（1 处，已裁决）

### C1 退出码语义冲突

| 来源 | 定义 |
|---|---|
| 经验库 §6.5 | `0`=正常（含跳过）· `1`=质量不达标（转 warning 继续）· `≥2`=真错误 |
| osslens 契约 | `0`=完成（**可能已降级**）· `1`=配置错误 · `2`=参数错误 |

**裁决：以 osslens 契约为准。** 理由是它已在 CODEBUDDY §2 与执行手册 §3 双处写死，且与 CI/调度耦合。

**映射表（避免 Agent 按经验库理解错）**

| 经验库的情形 | 在 osslens 中的落地 |
|---|---|
| 质量不达标 | **退出码 0** + 降级标记写进报告元数据块 + `costs.jsonl`（不是退出码 1） |
| 可选源失败 / 未配 key / 配额耗尽 / 预算拦截 | **退出码 0** + 留痕（不是失败） |
| 配置错误 | 退出码 1 |
| 参数错误 | 退出码 2 |
| 真错误（异常） | 兜底返回 1，**并**在报告与 `costs.jsonl` 双写 |

> ★ 这就是为什么必须钉死权威顺序：经验库这条本身没错（它服务的是别的项目），
> 但直接套用到 osslens 会让"配额耗尽"被当成失败——**而 osslens 明确要求它是正常完成**。

## 2. 需澄清的边界（1 处）

### C2 降档的定位

| 来源 | 说法 |
|---|---|
| 经验库 §7.15 省钱顺序 | 持久化 > 缩小范围 > 按条件跳过 > **降档（最不推荐，它削减的是价值）** |
| osslens | 档位是成本控制的核心机制，配额/预算耗尽即降级 |

**澄清：两者不冲突，osslens 的降级是第四顺位兜底，不是省钱手段。**

| 省钱顺位 | osslens 的对应实现 | 状态 |
|---|---|---|
| ① 结果持久化 | 外部快照落盘 + sha256；同一输入不重复调用 | ✅ 已设计 |
| ② 缩小作用范围 | **不喂整仓**（实测：元数据仅占源码 0.76%–9.36%）；上下文按信息密度裁剪 | ✅ 已设计（★ 最大杠杆） |
| ③ 按条件跳过 | 观察期未满不进深挖；off 档零 LLM | ✅ 已设计 |
| ④ 降档 | 仅当**配额/预算闸门触发**时降级 | ✅ 兜底，且必须双写留痕 |

> ★ 一句话给 Agent：**不要为了省钱主动降档；降档只在闸门触发时发生，且必须留痕。**

## 3. 正向印证（经验库印证了 osslens 的设计是对的）

这几条是**两个独立来源得出同一结论**，可信度最高，Agent 不必再质疑：

| osslens 的设计 | 经验库印证 |
|---|---|
| watchlist 是意图层，不是入口过滤器（设计方案 §6.4） | §4.7 / §8-12 **层次不能混用**——"意图层尤其危险，它长得像过滤器，但不是"，且注明"三次踩中" |

| 不引入 openai SDK（httpx 直连） | §9.1 可测试性一票否决（官方 SDK 让覆盖率 0%） |

| 文档三层归属（意图层决策者执笔 / 证据层 Agent 写 / 门面层跟代码） | §11.4 文档体系三层 + 一类 |

## 8. ★ init 不可漂移锚（v1.1 新增，2026-11-03）

> **背景**：`/init` 每阶段会**改写 / 优化 `CODEBUDDY.md`**（它是 Agent 自维护文件）。这是预期行为，不是异常。
> 若权威条目只存在 CODEBUDDY 里，一次"优化"就可能把它们稀释掉。
> **解法不是阻止改写，是让改写伤不到权威**：把它们收进**本文件**（Chat 助手维护、仓库内、**Agent 只读**）。

### 8.1 权威归属声明（★ 只声明与索引，不重抄条目）

| 条目 | 唯一权威位置 |
|---|---|
| 权威顺序（含"经验库是建议不是规格"） | 本文件 §0 |
| **C1 退出码裁决** / 映射表 | 本文件 §1 |
| **C2 降档定位** / 省钱四顺位 | 本文件 §2 |
| **N1–N12 新增纳入条目** | 本文件 §5 |
| 三条使用纪律 / 两份 `docs/ref/` 禁读约束 | 本文件 §7 |
| 15 条已内化 / 3 条不适用 | 本文件 §4 / §6 |

> ★ **`CODEBUDDY.md` 只保留一行引用**：
> 「§11 外部经验库的权威内容见 `docs/经验库-冲突与覆盖清单.md` §0–§8；本文件不复制。」
> ★ 其余按 `CODEBUDDY.md` §0 的权威顺序执行；**本文件与 CODEBUDDY 冲突时，以本文件为准**并上报。

### 8.2 `/init` 后必做的 diff 审阅（审阅，不是停工）

```bash
git diff -- CODEBUDDY.md
```

核对 5 个锚点**仍在**（不必逐字相同，语义不得丢失）：

- [ ] §0 权威顺序含「经验库是建议，不是规格」
- [ ] §4 最高 12 条 + 项目特有 8 条红线未被稀释
- [ ] §11 外部经验库：两处 C1/C2 裁决、N1–N12、两份 `docs/ref/` 禁读约束（或改为指向本文件 §8 的引用）
- [ ] §3 契约测试清单：L1 两条「存在」、L3 两条「⬜ 待建」状态未被重置
- [ ] 「禁止 force 更新 tag」「`l0`=792894d、`l1`=289beed 冻结」仍在

| 情形 | 动作 |
|---|---|
| 锚点齐全 | 继续，init 改写单独一个 commit（N6：一类改动） |
| 锚点丢失 | **从本文件 / SSOT 回填**，不是停工上报；在验收报告注明"init 稀释了哪些段落" |
| `/init` 新建了第二份指导文件 | 停下上报 → 裁决哪份是唯一入口（避免两处真相） |

### 8.3 每阶段固定顺序

```
/clear → /init → git diff CODEBUDDY.md 审阅锚点 → 输入开场指令 → 粘贴该阶段任务卡 → 开工
```

★ **`/clear` 前**必须确认上阶段结论已落盘（维护日志 tag 列 + 经验固化），否则上下文一清就丢了。
