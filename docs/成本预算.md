## 0. 已知账外支出（2026-11-05）

> ★ **本节不是台账，不参与 `cost` 命令统计，仅说明已知偏差**，避免与 `data/costs/costs.jsonl` 形成两处真相。

| 项 | 值 |
|---|---|
| 时间 | 2026-11-05，L2 开工前核对阶段（凭据有效性预检） |
| 模型 | `deepseek-v4-pro` |
| 用量 | 输入 84 tok / 输出 **16 tok**（`completion_tokens_details.reasoning_tokens = 16`）/ 合计 100 tok |
| 原因 | 开工前核对越界发裸 `httpx` ping：验证「凭据就绪」本应止于 `llm_credentials() is not None`，有效性应由 T1 正式实跑自证；该请求绕过 `osslens` 链路，无报告、无特征卡、无 `--dry-run` |
| 费用量级 | ≈ ¥0.0004（84×9/M + 16×27/M，高峰价单值；低谷约一半） |
| 处置（③′） | **不补记 `costs.jsonl`**，真源不因该笔增加行；不占 strong 周配额、不改配额计数、不新建 `source` 类型 |

**为何不补记**：`costs.jsonl` 是账户实际花的钱的 append-only 台账，但它同时是配额/累计统计的输入。补记会让「一次越界核对」变成一次正式 strong 调用，污染周配额（strong ≤1）与成本分布；且该请求没有对应的报告/特征卡/run_id，补一条孤立的 `call` 会制造"账实不符"的第二种形式。故选择**在证据层显式披露偏差**，而不是往真源里塞一条无法自洽的记录。

★ 台账 7 → 8 → 9 行的增长**不是**这笔补记：第 8 行是 T1 正式 strong 实跑的 `call`（见 §2），第 9 行是同 `--as-of` 重跑的 `cache_hit`，两者都是合法任务事件、有完整报告与 usage。本节的账外支出在 `costs.jsonl` 里**没有任何对应行**。

## 2. 估算 → 实测（分列，不混写）

| 项 | 估算 | 实测（2026-11-03，DeepEP） | 偏差 |
|---|---:|---:|---:|
| fast 输入 token | 17,354（按字符数 /4） | **21,803**（`usage.prompt_tokens`） | **+25.6%** |
| 其中缓存命中 | 0 | **896** | — |
| fast 输出 token | 未估 | **501** | — |
| fast 单次费用 | ¥0.0347 | **¥0.0459** | +32% |

**结论**：`len(text)//4` 只能当量级估算，**不得**用于对账；对账一律用 API 回显的 `usage`。
估算偏差主要来自 system prompt、文件清单与 JSON 包装（估算只覆盖用户正文）。

| 档位 | 单次费用 | 依据 |
|---|---:|---|
| fast（实测） | **¥0.0459** | 3 次真实调用，见 §4 |
| strong（**L2 实测**） | **¥0.4174** | 见 §2.1；原估算 ≈ ¥1.12（假设 100k 输入）高估 2.7× |

### 2.1 strong 实测（2026-11-05，DeepEP，`--depth strong`）

真实 `usage` 回显（非单测输出，见 `data/costs/costs.jsonl` 第 8 行 / 报告「成本说明」行）：

```
model=deepseek-v4-pro  format=json_object  thinking=on
prompt_tokens=21910  cache_hit=0  cache_miss=21910
completion_tokens=8156  其中 reasoning_tokens=7801  total=30066
estimated_cost=¥0.4174  （21910×9/M + 8156×27/M = 0.417402）
```

★ **reasoning token 计入输出计费**：API 把 reasoning 含在 `completion_tokens` 内，按输出单价计费一次，**不重复计费**；`reasoning_tokens` 单列只为可核验留痕（`Usage.reasoning_tokens` / 台账 `reasoning_tokens` 字段）。
★ **洞见带证据**：5 条，每条带 `file:line`（`README.md`、`deep_ep/buffers/ep.py`），由 `validate_insight` 校验路径合法；报告区块数仍为 5，同 `--as-of` 重跑 sha256 一致（缓存命中，未二次调用）。

**估算 vs 实测偏差（D12-2）**：
L1 的 `len(text)//4` 估算 17,354，实测 21,803（**低估 25.6%**）。strong 本次上下文估算 17,280、实测输入 21,910（低估 26.8%）——两档同向低估，故新增 `budget.estimate_safety_factor = 1.3`，闸门按 `估算×1.3` 判断（17,280 → 22,464）。反向测试见 `tests/test_l2.py::test_safety_factor_blocks_l1_underestimate`：限额 20,000 时系数 1.0 漏拦、1.3 拦下。

**周/月/年（1 strong + 3 fast 的周配额节奏，全部按实测）**：

| 窗口 | 高峰价 | 低谷约一半 |
|---|---:|---:|
| 周（1×0.4174 + 3×0.0459） | **¥0.5551** | ≈ ¥0.278 |
| 月（52/12 周） | **¥2.4054** | ≈ ¥1.203 |
| 年（52 周） | **¥28.8652** | ≈ ¥14.433 |

> L1 原估算（strong ≈¥1.12 假设 100k 输入）推得年 ≈¥65；L2 实测把稳态年成本**下修到 ¥28.87**，原因是实际上下文仅 21.9k tok、单次 ¥0.4174。

**M9 年化义务（改阈值给改前/改后 × 365）**：
`estimate_safety_factor` 只改闸门判定、不改单价与配额 → 年化成本改前 ¥28.87 → 改后 ¥28.87（差 ¥0.00 × 365 = ¥0.00）；等效的单次上限由 120,000 tok 收窄为 92,307 tok。真正改变年化成本的是**实测替换估算**（¥65 → ¥28.87），已在上表列明。

## 3. M1 · 报告里的成本说明块

**位置**：`## 运行元数据` 块内追加三行，**不新增第六区块**（避免改 SSOT 报告结构）。

```
| 成本说明 | 本次 ¥0.0459（模型调用 1 次）；输入 21,803 tok / 命中 896 tok / 输出 501 tok |
| 累计 | 本周 ¥0.0459 / 22,304 tok；本月 ¥0.0459 / 22,304 tok |
| 单价 | deepseek-flash 输入未命中 ¥2/M · 缓存命中 ¥0.04/M · 输出 ¥8/M（官方中文页，核对 2026-11-03，取高峰价；低谷约为一半） |
```

★ **口径（重要）**：报告描述「**本次分析的成本**」，与「本次进程是否命中结果缓存」无关。
同一 `--as-of` 重跑时，成本行不变（否则幂等失效）。进程级的真实花钱情况看 `cost` 命令。

该口径已**写进报告本身**（`运行元数据` 块第 4 行）：

```
| 口径 | 本次分析的成本（不含开发期重复调用）；账户累计见 cost；成本说明同 as-of 重跑不变（幂等优先）；两者不一致是设计，不是 bug |
```

→ 读者不会再把它误读成"台账漏记"。D10 = A 的显式字样由 `osslens/render.py` 的 `D10_WORDING` 常量写死，`tests/test_l2.py` 有断言防稀释；`cost` 命令口径**不变**（仍读完整台账）。

## 4. M3 · 真源 vs 缓存

| 文件 | 性质 | 说明 |
|---|---|---|
| `data/costs/costs.jsonl` | **真源**（append-only，跟 git 走） | 每次调用/降级/拦截/缓存命中都记一行 |
| `data/llm_cache/<sha256>.json` | 缓存（可丢弃） | 同输入复用，删掉只会多花钱，不会丢结论 |
| `data/snapshots/**/src/` | 缓存（可丢弃） | 由 commit 决定，可重建 |
| `data/snapshots/**/external/` | ★ **不可再生真源** | 外部索引状态 + 四元组，错过不可复现，**不删不覆盖** |

★ 归类唯一权威 = `docs/设计方案.md` §8.2（v1.3，D15）。红线 #6 的 append-only 清单只含 3 个 jsonl + `patterns/`，**从未含 snapshots 整块**；清理 `src/` / `llm_cache/` 不违规。本表是证据层，与 SSOT 一致，不再冲突。

**坏记录**：解析失败 / 费用为 `null` / 时间非法 → **打印提示，不静默跳过**（少算比多报更危险）。

**台账实测（截至 2026-11-03）**：

```
本周 tokens 67,168（缓存命中 1,152），费用 0.1421，降级 2 次，预算拦截 0 次
按档位 fast=3；按用途 fast_insight 3 次 67,168 tok
```

> 3 次调用来自 L1 开发期的三次迭代（改 prompt/图结构各触发一次真实调用），
> 不是产品缺陷，保留在台账里作为真实审计痕迹。

| 单次突增 | 本次 > 同仓库历史调用中位数 × 3 | 同上；**中位数为 0 时跳过**（不拿 0 冒充） |

- 月阈值 = 6,000,000 × 80% = 4,800,000 tok → 实际 1.621%，**未触发**；

★ 成本异常**不写入 `degraded`**：`degraded` 只表示数据源故障，混入成本会变噪音。

| 环节 | 实现 | 落点 |

| 触发 | `abstract.cluster_min_new_projects`（默认 6，config 可配） | 未达阈值 → `insufficient_samples`，**0 次调用** |
